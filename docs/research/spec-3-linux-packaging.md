# Spec 3 research: the Linux package

## Question

How should Phase 1 ship as one installable Linux package holding the built interface (`ui/dist`), the engine service, the Phase 1 engines (SimPy, HiGHS through `highspy`, Pyomo, Optuna, and everything else `pyproject.toml` needs at run time), the ten templates and the desktop shell (`desktop/`, AKS-142), so that it installs and runs offline once downloaded (spec 0 principle 6), on a Linux machine that may not have a suitable Python? Which format is simplest while meeting spec 3 "Packaging", and is every bundled component's licence compatible with distributing the whole under AGPL-3.0? (Spec 3 "Packaging"; AKS-127; owner decision B4 of 2026-11-09, Linux only.)

## Finding

What the package must carry, measured on 2026-11-09 in the agent container (Ubuntu 24.04, x86_64):

- **Python.** The service needs Python 3.11 or later (`requires-python`). Ubuntu 22.04's system Python is 3.10; Ubuntu 24.04's is 3.12 but its `venv` module (`python3-venv`) is not installed by default, and a minimal `ubuntu:24.04` container has no Python at all. So the package cannot rely on the system Python.
- **Run-time dependencies.** Resolving `pyproject.toml`'s run-time dependencies for CPython 3.13 on manylinux x86_64, at the versions the development environment tests (`pip install --dry-run --report`, with the development environment's `pip freeze` as constraints), gives 52 distributions, all as binary wheels on PyPI. Installed they take about 570 MB (pyarrow 170 MB, scipy 140 MB with its libraries, pyomo 54 MB, numpy 70 MB with its libraries). The highest platform tag among them is `cryptography`'s `manylinux_2_34`, so the service needs glibc 2.34 or later (Ubuntu 22.04 has 2.35, Debian 12 2.36).
- **The service starts child processes as `sys.executable -m ...`**: the launcher starts `python -m lcsim.service`, the service starts each run's worker as `python -m lcsim.runs.worker`, and the desktop shell runs `$LCSIM_PYTHON -m lcsim.launcher`. Whatever ships must therefore be a real Python interpreter that takes `-m`, not a frozen program.
- **The desktop shell** (built on Ubuntu 24.04 with Tauri 2.12.5, 3.5 MB) links the system's WebKitGTK 4.1, GTK 3 and libsoup 3 (DECISIONS AKS-142) and needs glibc 2.39 (`objdump -T`: the newest symbol version is `GLIBC_2.39`), so it runs on Ubuntu 24.04 or later. Tauri's documentation says to build on the oldest system to be supported ("Ubuntu 22.04 and Debian 12 are suitable baseline examples").

Python-build-standalone (read 2026-11-09 from <https://gregoryszorc.com/docs/python-build-standalone/main/running.html> and `quirks.html`): its "install_only" archives are a CPython installation that runs from any folder (`libpython` is found through `$ORIGIN`); "We build CPython against libedit - as opposed to readline - to avoid this GPL dependency" and "globally disable the `_gdbm` extension module"; the terminfo database is looked for in `/etc/terminfo`, `/lib/terminfo` and `/usr/share/terminfo`. Release `20261020` provides `cpython-3.13.16+20261020-x86_64-unknown-linux-gnu-install_only_stripped.tar.gz`, 35.4 MB, SHA-256 `f326b7a386bf22def82e55dc3b95d2bef8b7c938b4c98ec32dd65433e7720b50` (from the release's `SHA256SUMS`, and checked on the downloaded file). The unstripped archive is 77 MB because `libpython3.13.so.1.0` keeps its symbols (140 MB installed), so the stripped one is used.

What the bundled Python contains, checked in the extracted archive: OpenSSL 3.5.9 (`ssl.OPENSSL_VERSION`), SQLite 3.53.1, zlib 1.3.2, libedit (the `readline` module's docstring names it), Expat 2.9.0, mpdecimal, libffi, liblzma, bzip2, Tcl/Tk 9.0.4, and Berkeley DB 6.0.19 behind `_dbm` (`_dbm.library` and the strings in the module). Its licence texts: CPython's `lib/python3.13/LICENSE.txt` covers CPython and lists the third-party code CPython itself carries; the other libraries' texts are not in the "install_only" archive (they are in the "full" archive), so the build writes their names, versions and licences into the package's `THIRD-PARTY-LICENSES.txt`.

Berkeley DB 6.0.19: AGPL-3.0 (Oracle relicensed Berkeley DB 6 under the AGPL; compatible, since the whole is distributed under AGPL-3.0).
- The 52 Python distributions: MIT, BSD-2-Clause, BSD-3-Clause, Apache-2.0, PSF-2.0, MIT-0, MPL-2.0 AND MIT (`tqdm`), Zlib, 0BSD and CC0-1.0 (parts of `numpy`), or a choice among these (`cryptography` Apache-2.0 OR BSD-3-Clause, `packaging` Apache-2.0 OR BSD-2-Clause). The numpy and scipy wheels carry `libgfortran` (GPL-3.0-or-later with the GCC Runtime Library Exception), `libquadmath` (LGPL-2.1-or-later) and OpenBLAS (BSD-3-Clause), listed in their own licence files; each is compatible with AGPL-3.0 (GPL-3.0 section 13 and AGPL-3.0 section 13 allow combining; LGPL and the runtime exception permit it).
- The interface's npm packages: the build of `ui/` already writes `THIRD-PARTY-NOTICES.txt` beside `index.html` (DECISIONS AKS-119); the desktop shell's crates are recorded in DECISIONS AKS-142 (MIT, Apache-2.0, BSD, ISC, Zlib, Unicode-3.0, MPL-2.0 and similar; none incompatible).
- Not shipped: WebKitGTK, GTK and libsoup (system libraries the shell loads, LGPL), glibc, `libstdc++` and `libgcc_s` (system libraries the wheels load).

## Decision

Option A, a self-contained archive (owner to confirm; candidate bucket Phase 1a):

- **One file**, `lcsim-<version>-linux-x86_64.tar.gz`, with `lcsim-<version>-linux-x86_64.tar.gz.sha256` beside it (the `sha256sum` format, so `sha256sum -c` checks it). Unsigned; the README and the archive's `INSTALL.txt` say so and how to check the checksum (spec 0 "Risks").
- **Inside**, one folder `lcsim-<version>-linux-x86_64/`: `python/` (the python-build-standalone CPython 3.13.16 with the 52 pinned wheels and the `lcsim` wheel installed into it), `python/share/lcsim/ui` (the built interface) and `python/share/lcsim/templates` (the ten template packages), `lib/lcsim-desktop` (the desktop shell), `bin/lcsim`, `bin/lcsim-launcher` and `bin/lcsim-mcp`, `install.sh`, `uninstall.sh`, `share/lcsim.png` (the shell's 128-pixel icon), `LICENSE`, `INSTALL.txt`, `THIRD-PARTY-LICENSES.txt` and `BUILD-INFO.json` (the commit and the pinned inputs).
- **Installing** is unpacking the archive in any folder (the instructions use `~/.local/opt`) and running `install.sh`, as the user, without network: it checks that the bundled Python and the engines import, links the three commands into `~/.local/bin`, writes a desktop entry to `~/.local/share/applications` (or under `$XDG_DATA_HOME`), and says whether the desktop shell can run here. `uninstall.sh` removes the links and the entry; the user's projects and settings stay.
- **Starting**: `lcsim` runs the desktop shell when there is a display and the shell's libraries are found (`ldd` reports none missing), with `LCSIM_PYTHON` naming the bundled Python; otherwise it runs the launcher, which opens the interface in the default browser, and says why on standard error (on Ubuntu, `sudo apt install libwebkit2gtk-4.1-0` brings the shell's libraries). `lcsim-launcher` is `python -m lcsim.launcher` with its options (`--print-url` for scripts and headless use), and `lcsim-mcp` is the MCP server for an assistant. Each command unsets `PYTHONHOME` and `PYTHONPATH` and sets `PYTHONNOUSERSITE=1` and `PYTHONSAFEPATH=1`, which the service and its run workers inherit, so packages in the user's own site folder or the current folder never shadow the bundled ones (the agent container's `~/.local/lib/python3.13/site-packages` held `conan` and 10 other distributions, which the bundled Python saw until isolated).
- **The service finds the interface and templates** by its defaults: `ui/dist` and `templates` beside `src/lcsim` in a source checkout, as before, or else `share/lcsim/ui` and `share/lcsim/templates` under the Python installation's prefix (`sys.prefix`), where the package puts them. Spec 3 names both.
- **Built** by `scripts/package_linux.py` from the repository: the interface (`npm ci`, `npm run build` in `ui/`) and the shell (`npm ci`, `npm run build` in `desktop/`) from their lock files; the Python archive downloaded once and checked against its pinned SHA-256; the wheels from `packaging/linux/requirements.lock` (exact versions and SHA-256 hashes, `pip install --require-hashes --only-binary=:all: --no-deps`); the `lcsim` wheel built from the checkout; licences checked against `packaging/linux/licences.json`, the build failing on any distribution not listed with its version; the archive written in a fixed order with fixed owners and times (`SOURCE_DATE_EPOCH`, the commit's time), into `dist/` (ignored).
- **Supported**: Linux x86_64 with glibc 2.39 or later for the desktop shell (Ubuntu 24.04, where it is built and tested), glibc 2.34 or later for the service and the browser path. Building the shell on Ubuntu 22.04 to widen this is left (candidate bucket Phase 1a).
- **Version**: the archive's name carries `lcsim.__version__`, still `0.0.0`; numbering the first release is the owner's (candidate bucket Phase 1a).

Rejected: B's `.deb` cannot install offline where WebKitGTK is missing, and its AppImage needs FUSE 2 that current Ubuntu lacks and still needs the Python tree of A; C needs a system Python 3.11 with `venv`, which is the problem; D needs the service's process model changed; E needs a runtime fetched from the network and a sandbox the local service and project folders fight. A also keeps the code platform-neutral (B4): the Windows package, when the Phase 1 review sets its phase, can take python-build-standalone's Windows build the same way.
