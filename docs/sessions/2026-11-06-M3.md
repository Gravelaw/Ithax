Candidate bucket: Phase 1a.
2. **Warm-up check readings.** Raised by PR #21 and the AKS-129 entry.
   - The paired-halves check is kept, at 99% and a 5% threshold, over MSER-5 and Welch's method. Candidate bucket: Phase 1a (thresholds revisited with the finding thresholds at M8 and M10).
   - It reads the `timeseries` samples as a plain sample mean, not a time-weighted integral, from `warmup` on. Candidate bucket: Phase 1a.
   - The halves are cut by sample count (the middle sample dropped when J is odd); a metric with J < 2 is skipped. Candidate bucket: Phase 1a.
   - The reference mean m̄ is the mean over replications of each replication's mean of all J samples; both comparisons are strict, so a constant series never fires. Candidate bucket: Phase 1a.
   - The level is 99% whatever the experiment's `confidence`. Candidate bucket: Phase 1a.
   - One W210 per run, listing each changed metric, `component` null, `path` `/experiments/<index>/warmup`, hint "Lengthen 'warmup' and run again.". Candidate bucket: Phase 1a.
   - A search's candidates are not checked; decided at M5. Candidate bucket: Phase 1a.
3. **Experiment manager readings.** Raised by PR #22 and the AKS-102 entry.
   - A NaN replication value is left out; mean and half-width are over the n values left, `n` is reported with every metric, the half-width is `null` when n = 1 and the mean too when n = 0. Candidate bucket: Phase 1a.
   - `differences` is a top-level list, one entry per pair of scenarios in the experiment's order, later minus earlier (`scenario` minus `against`); a replication is paired only when both values are not NaN. Candidate bucket: Phase 1a.
   - `separated` is n ≥ 2 and |mean| > half-width, strictly. Candidate bucket: Phase 1a.
   - `summary.json` key order follows the spec 1 example, metrics follow the `replications` table's rows, scenarios the experiment's order; a scenario's `set` is in SI units. Candidate bucket: Phase 1a.
   - `warnings` order: load-time warnings (added by AKS-103), the adapter's `validate` warnings, `collect`'s, then W210. Candidate bucket: Phase 1a.
   - `fidelity_label` reads "<Fidelity>: <n> replications of <length>, <confidence>% confidence", the length a whole number in the largest unit that gives one (`d`, `h`, `min`, else `s`; 48 h is "2 d"), the percentage without a trailing `.0`. Candidate bucket: Phase 1a.
   - The optimization `summary.json` is `model`, the adapter's `solution`, `fidelity_label` ("Standard") and `warnings`; not run until M5. Candidate bucket: Phase 1a.
   - Warm-up edge cases: a metric with m̄ = 0 is not reported as changed; the percentage rounds a half up; fewer than 2 replications is not checked (and unequal sample counts raise); a search experiment is refused with `NotImplementedError` until M5. Candidate bucket: Phase 1a.
   - E173 refuses a `run.fidelity` other than `standard` before anything is translated. Candidate bucket: Phase 1a.
4. **Local run target readings.** Raised by PR #24 and the AKS-103 entry. (The `queued` → `failed` move is item 1.)
   - `validate`, `translate` and `collect` run in the process that drives the run; `run` runs in a worker started with `spawn` that creates the adapter's class with no arguments and is not a daemon. Candidate bucket: Phase 1a.
   - Refusals happen before a run exists, in this order: load errors, E172 for a `run.target` other than `local`, E102, then `validate` and E173; no `run_id` and no folder are created. Candidate bucket: Phase 1a.
   - `model.json` is the file's exact bytes, not a re-serialised model; a seed chosen at load is recorded only in the manifest. Candidate bucket: Phase 1a.
   - Manifest values: `fraction` is the progress (0 queued, each reported fraction, 1 at `done`; kept on cancel or failure), written on the first report and then at most once a second; the progress message is not written; `project_id` is null and `client` is `script` until M6; `host` is the host name; times are ISO 8601 UTC to the millisecond with `Z`; `error` only on a failed run; `data_files` stays empty until M6. Candidate bucket: Phase 1a.
   - E191 is detected through an exclusive OS lock on `worker.lock` held by the driving process (`fcntl.flock` or `msvcrt.locking`), not a pid file. Candidate bucket: Phase 1a.
   - E192: limits are `LocalTarget` parameters (10 min, half of physical memory); time from `started`, checked every 0.1 s; memory is the resident memory of the worker and all its descendants, read from `/proc` once a second; the worker gets 2 s, then is terminated. Memory is not enforced on Windows or macOS (no `/proc`), and `log.txt` says so. Candidate bucket: Phase 1a (closed with packaging at M11 or by AKS-77).
   - `summary.json` `warnings` start with the load-time warnings W200 to W202. Candidate bucket: Phase 1a.
   - The worker CLI contract: `python -m lcsim.runs.worker <workdir> [--workers N]`, the adapter named by `engine.name` in `<workdir>/../manifest.json`, a `CANCEL` file as the token (looked at at most every 0.05 s), JSON progress lines on standard output, exit 0 done, 1 error, 2 usage, 3 cancelled; it enforces no limits itself. Candidate bucket: Phase 1a (used by the remote and cluster targets at M11).
   - The six `run_id` characters come from `secrets` (an identifier, not simulation randomness). Candidate bucket: Phase 1a.
   - Platform-neutral code pending AKS-77: `spawn` only, no signals beyond `terminate` and `kill`, guarded `/proc` reading, the lock chosen by `os.name`; not run on Windows in this session. Candidate bucket: Phase 1a.
   - From the review rounds: a cancel arriving during `collect` still ends the run `cancelled` with no results; the worker is watched until its process ends, not until its pipe closes; a terminated worker's own processes are ended with it where `/proc` finds them (only the worker on Windows and macOS); a worker still running 2 s after `terminate` is killed; the 5 s cancel grace counts from the first cancel; a worker that cannot be started is E190. Candidate bucket: Phase 1a.
