Ithax interface design walkthrough

This page shows the interface design for Ithax, in the order we walk through it in conversation. The pictures are the real wireframes from docs/design/wireframes/, not redrawn. They are low-fidelity plans of each screen, drawn in the light theme. Numbers inside them are examples.

1

The two user flows

A flow is the path a person takes from opening the app to seeing a first result. There are two, one for each kind of user. Both use the same canvas and the same model file, so a learner and a builder see the same tool.

Shared start: Install→Start app→Engine service starts→First-start notice (once)→Home

Learn mode

For a student who wants to understand a method.

  1. On Home, choose Learn and pick a lesson, for example "Coffee shop queue".
  2. The Canvas opens with a step card. Each step highlights one block and explains it.
  3. The exercise asks for one change, such as 1 till to 2 tills.
  4. The student picks a prediction ("the wait will fall by about half"). Only then does the card's Run button turn on.
  5. Run → Run monitor → Results. Results show "You predicted: …" and the explanation first.

Why: predicting before running is what makes the lesson stick. The student can leave the lesson at any step and keep the project.

Build mode

For a business user with a real question.

  1. On Home, choose Build. A fixed two-question form opens (not a chat).
  2. Q1 "What do you want to find out?" Six answers, each opening a template. The "best mix, plan or rota" answer asks one more question.
  3. Q2 "Do you have data?" No → Canvas with the numbers to edit. Yes → Data screen to import a file and fit it.
  4. Change numbers, optionally set the experiment, then Run.
  5. Run monitor → Results, findings first.

Why: a business user starts from their question, not from a blank canvas. Data is never required, so nobody gets stuck for lack of a file.

Error paths are planned too: the service does not start, the connection drops (the canvas goes read-only, runs keep going), a file cannot be read, a run fails. Each one shows a plain message and a way forward.

The Canvas, the heart of the app

The canvas is where a model is built: blocks are steps in a process (arrivals, a till, an exit), lines show where items go next. Three wireframes cover it.

Canvas, Build mode

01-canvas.svg ↗
  • Left: the palette of block types, in three colour groups. Drag one out, or click it and click the canvas.
  • Centre: the coffee shop model. A newly added server_2 has a red badge because a required setting is still empty.
  • Right: the side panel shows the selected block's settings. With nothing selected it shows the model's parameters.
  • Bottom: the problems list. Clicking a problem selects the block.
  • Top: "Saved" status (there is no save button), Undo, Redo, and Run. Run is greyed out with the reason written beside it: "1 error. Fix it to run."

Why: the same three-column layout as JaamSim, AnyLogic and FlexSim, so it feels familiar. The reason for a disabled Run is written out because users otherwise cannot tell why nothing happens.

Canvas, Learn mode

01b-canvas-learn.svg ↗
  • The step card sits above the side panel: "Step 2 of 5", short text, Back, Next, Exit lesson.
  • The step's block gets a purple ring and a tag. Other blocks are not faded, so they stay readable.
  • The canvas stays editable during a lesson.

Block and port states

01c-canvas-states.svg ↗
  • Every state has a shape or word as well as a colour: errors are a round badge, warnings a triangle.
  • Blocks with no in/out ports (resource pool, schedule, failure) have a dashed outline. Their links to other blocks are dashed "reference lines", set in the side panel.
  • While connecting, every place you can drop the line gets a blue ring.

The other screens

Spec 3 lists seven screens. The navigation rail on the left of every screen lists them in this order. The Build form and the first-start notice are shown too.

Home

02-home.svg ↗

Two big doors, Learn and Build. Below them the ten templates, each with its audience and estimated minutes, and recent projects. Projects an assistant built show up here too.

Build form

02b-build-form.svg ↗

Two questions on one page. Each answer shows which template it opens, so the user knows what they will get before pressing Continue.

Data

03-data.svg ↗

Import a CSV or Excel file, pick a column such as "minutes between arrivals", and press Fit a distribution. The app lists the best-fitting patterns. "Use for…" puts the chosen one straight into a block's setting, or uses the raw data as it is.

Experiment

04-experiment.svg ↗

How long to simulate, how many repeats, and "what if" scenarios side by side (for example 1, 2 or 3 tills). Templates come with sensible values, so beginners can skip this screen.

Run monitor

05-run-monitor.svg ↗

A progress bar with a plain message ("Scenario 1 of 2, replication 12 of 30"), live numbers that update at most once a second, a Pause updates button, and Cancel. Runs keep going if the window is closed; reopening shows the progress again.

Results

06-results.svg ↗

Findings in plain words come first ("Machine 2 is the bottleneck…"), then key numbers with their uncertainty range, then charts (each with a data table beside it), then tables. Export to CSV, PDF or a zip of the project. Every page ends with the footer the spec requires, including "Simulation results are estimates and carry no warranty."

Settings

07-settings.svg ↗

Where runs happen, how many at once, the hardware tier (detected, but changeable), installed engines, theme and text size, and the licence.

First-start notice

08-first-start-notice.svg ↗

Shown once. Three short paragraphs: what the tool does, that results are estimates to support judgement, and where to read the licence. One button: Continue.

4

How the canvas behaves

The rules in canvas-interactions.md, in short. One idea runs through all of them: the canvas only ever shows the saved model file. Every action is a small change sent to the engine service, and the canvas redraws from what the service says back.

ActionHow it works
AddDrag from the palette, or click then click, or Enter from the keyboard. New blocks are named server_1, server_2…
ConnectDrag from an output dot to an input dot, or click then click, or press C, or use the side panel. Re-connecting an output replaces the old line, and a notice says what it was.
SelectClick, Ctrl+click for more, Shift+drag for a box, Ctrl+F to find by name.
DeleteNo "are you sure?" box. A notice says what went, and Undo brings it back.
Undo / redoCtrl+Z / Ctrl+Y, 200 steps. Each step restores the whole earlier model.
Zoom20% to 200%, Fit button, minimap. Below 50% blocks show just colour, icon and badges.
SaveAutomatic. The top bar says "Saved" or "Saving…". If the service stops answering, the canvas pauses and retries.
ErrorsChecked half a second after each change. Badge on the block, entry in the problems list, message under the field.
Someone else editsIf an assistant changes the model, the canvas reloads and says so in one line.

Not in Phase 1: grouping, sub-models, copy and paste, comments on the canvas, alignment tools.

  • Three block colours: teal for things that move items (source, sink, delay, branch), violet for things that work on or hold items (server, queue, store…), brown for things that change other blocks (resource pool, schedule, failure).
  • Type: body text 14 px, smallest text 12 px, all scalable to 200%. Names like till.wait.mean use a monospace font.
  • Contrast: all 56 colour pairs pass the WCAG 2.2 AA standard. Lowest text pair 5.19:1 (minimum 4.5:1).
6

Accessibility

The target is WCAG 2.2 Level AA, the common standard for accessible software. In practice that means:

  • Everything works from the keyboard. Every drag has a keyboard path and a click-only path (for example click a port, then click another port).
  • Never colour alone. Errors and warnings differ by shape and word; chart lines have different marker shapes.
  • Readable. Strong contrast, text size up to 200%, a visible focus ring on everything you can tab to.
  • Screen readers. Blocks read as "till, server, capacity 1, 1 error". With nothing selected, the side panel lists every block as a table, a text version of the whole drawing.
  • Calm. No animation; live numbers can be paused.

Not yet tested with a real screen reader or keyboard-only user. That happens once the interface exists (M9).

Twelve design choices for you to confirm

Where the specs said nothing, the design took the simplest reading. Each is listed in docs/DECISIONS.md (6 November) as waiting for you. For each: confirm it, or say what to change.

1

Undo stores whole copies of the model, 200 steps

ChoiceUndo puts back the whole earlier model. 200 steps kept (spec asks for at least 100).

AlternativeUndo by sending the opposite change.

ReasonSome changes have no opposite (adding an optional setting cannot be removed by any edit). Costs a few MB of memory.

2

An outside edit reloads the canvas and clears undo

ChoiceIf an assistant or script changes the model, the canvas reloads, says so, and clears undo history.

AlternativeKeep the undo history.

ReasonAn undo could silently wipe out the assistant's change.

3

Port-less blocks use dashed reference lines

ChoiceResource pool, schedule and failure are linked with dashed lines, set in the side panel.

AlternativeLet users drag to link them.

ReasonThese blocks have no ports in spec 2; items never flow through them.

4

Optimization models get a form, not a drawing

ChoiceProduct mix, transport plan and staff rota show tables of variables, objective and constraints.

AlternativeDraw them as a graph.

ReasonThese models have no blocks or flows to draw.

5

New block names and positions

ChoiceNames are server_1, server_2… using the smallest free number. Position is stored as x and y.

AlternativeRandom ids, or always counting up.

ReasonMatches the spec's own example and JaamSim's habit; easy to read.

6

No grouping, sub-models, copy-paste or canvas comments in Phase 1

ChoiceLeave them out.

AlternativeAdd one or more now.

ReasonNot required by spec 3, and the model file has no place to store them.

7

Zoom 20%–200%; one drag is one undo step

ChoiceWider zoom range than the library default. A drag, or a burst of arrow-key moves, undoes in one go.

AlternativeLibrary default 50%–200%; one undo step per arrow press.

Reason200 blocks must fit on one screen; undoing a move pixel by pixel is tiresome.

8

When saving fails, pause and retry

ChoiceCanvas goes read-only and retries every 2 seconds; nothing else is queued.

AlternativeLet the user keep editing and queue the changes.

ReasonThe user should never pile up work the service has not seen.

9

Run waits for saving and checking

ChoiceRun is also disabled while a save or check is in progress, with "Saving…" or "Checking…" beside it.

AlternativeAllow Run at any time.

ReasonA run never starts on a model the user has not seen checked.

10

Settings: tier, theme, text size

ChoiceThe user can override the detected hardware tier. Theme: System, Light, Dark. Text size 100%–200%.

AlternativeTier fixed by detection; one theme.

ReasonDetection can be wrong; accessibility needs text scaling.

11

System fonts only

ChoiceUse fonts already on Windows and Linux.

AlternativeBundle a brand font.

ReasonNothing is downloaded (spec 0, works offline); no font licence to check.

12

Three block categories

ChoiceFlow (source, sink, delay, branch), work (server, queue, batch, unbatch, store), resource (resource pool, schedule, failure).

AlternativeOne flat alphabetical list, or other groupings.

ReasonGroups by what a block does, which is how a beginner looks for it.

8

Two API additions and one open gap

The design found places where the model could not be edited at all. Two were fixed in spec 3. One is left for M6.

A

New edit: set_label

AddedAn edit that sets a block's display name, such as "Front counter" for till.

AlternativeAddress the label by list position, or make labels read-only.

ReasonSpec 1 allows labels, but no edit could set one. Positions break when blocks are added or removed.

B

set_path reaches variables and objective

AddedThe general edit can now change an optimization model's variables and objective.

AlternativeA separate edit for each.

ReasonWithout it, neither the form (choice 4) nor an assistant could edit an optimization model.

!

Open, for M6: no edit can set domain

EffectA new empty project is always a process model. An optimization model can only start from a template or a whole-file upload.

OptionsLet "New empty project" take a domain; or add a domain edit; or leave it, since the three optimization templates cover Phase 1.

QuestionWhich do you prefer, or should M6 decide?

What this review is not

Today's session is your own review as owner. Spec 3 asks for something different before interface code starts: a walkthrough of these wireframes with at least one student and one business user from outside the project. They see the design with fresh eyes; you know too much about it to spot what confuses a newcomer.

Spec 3 has a fallback if nobody outside is available within two weeks: you do a scripted think-aloud walkthrough (you follow written tasks and say aloud what you expect and notice), log the gap in DECISIONS, and the outside walkthrough moves to a condition of M10 instead of M9.
