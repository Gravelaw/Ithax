# Spec 3: Desktop Application

> Version 0.5 · working copy in the repository (source of truth, owner to confirm) · changes are listed under "Changes in this version".

The app is two programs: an engine service that does all the work, and an interface that talks to it only through an API. That split is what lets a Windows interface drive Linux engines.

> **Warning: partly tested.** The engine service and its API were built at M6 (AKS-110 to AKS-114): the service rules, every row of "Endpoints", "Model edits", "Status codes and errors", "Progress events" and "Project folder", with the three M6 acceptance rows passing; from M8 the run summary carries the findings of spec 4 at the thresholds of `settings.json` (AKS-135); from M9 the service serves the interface, with the launcher, the settings endpoint, the interface shell, the first-start notice and Home built (AKS-119), the Canvas of a `process` model (AKS-136), and the review of outside changes and the Table and Diagram views of an `optimization` model (AKS-137), and the Data and Experiment screens (AKS-120); the other screens, the desktop shell and packaging have not been built. The interface frameworks were re-checked on 2026-11-06 (`docs/research/spec-3-framework-check.md`) and the service framework on 2026-11-07 (`docs/research/spec-3-service-framework-check.md`). The performance targets are proposals; the three service targets were measured at M6 (`docs/research/perf-M6.md`), not yet on the low tier. This spec defines behaviour; the user flows, wireframes, canvas rules, design system and accessibility check are in `docs/design/` (2026-11-06), and the owner reviewed them on 2026-11-06 (design system version 2; `docs/DECISIONS.md` "Owner design review"). The walkthrough with outside users has not happened; the owner took the fallback below, so it is a condition of M10. See "Known gaps" in the Build guide.

## Scope

- **In:** the engine service, its API, the interface, project storage, data import, packaging, hardware tiers.
- **Out:** the model format (spec 1), engines (specs 2, 5, 6), templates and assistant tools (spec 4).

## Architecture

| Part | Role | Proposed technology |
| --- | --- | --- |
| Engine service | Validates models, schedules runs, hosts engine adapters, serves results | Python with FastAPI 0.162.1 or later, served by uvicorn 0.54.0 or later with websockets (never `uvicorn[standard]`, whose uvloop has no Windows build); confirmed 2026-11-07 (`docs/research/spec-3-service-framework-check.md`; licences in `docs/DECISIONS.md`) |
| API | The only way in: HTTP for requests, WebSocket for live progress | Local address only by default |
| Interface | Canvas, forms, charts | React with React Flow (`@xyflow/react`), packaged as a desktop app with Tauri 2, version 2.11.1 or later (confirmed 2026-11-06; licences in `docs/DECISIONS.md`) |
| Storage | One folder per project: model file, imported data, runs | Files, plus SQLite as a run index |

On Linux both parts run natively. On Windows, Phase 1 runs both parts natively (proposed default from the review, owner to confirm): every Phase 1 dependency ships Windows wheels or is pure Python (highspy, numpy, scipy, pyarrow, pyomo, simpy, optuna, pint, fastapi; PyPI file lists read on 2026-11-05), while WSL costs an administrator install, a restart and by default half the memory of a low-tier machine. A WSL path is added in Phase 3 for engines without Windows builds. Until the owner decides, service code must stay platform-neutral (no fork-only process code, no Linux-only paths).

## API

| Endpoint | Purpose |
| --- | --- |
| `/projects` | Create, open, list |
| `/models` | Read and write the model file |
| `/validate` | Run both validation passes |
| `/runs` | Start, cancel, list; `/runs/{id}/events` streams progress |
| `/results` | Summary and tables (fields arrive with spec 6) |
| `/engines` | Installed adapters and their capabilities |
| `/system` | Detected hardware and the active tier |
| `/settings` | The user's settings: tier, run settings, finding thresholds, interface preferences |

The interface uses no private channel. Anything it can do, a script or an assistant can do through the same API.

## Screens

1. **Home:** recent projects, template gallery, Learn or Build entry (Build mode form as in spec 4).
2. **Canvas:** drag blocks from a palette, connect them, edit properties in a side panel. Validation errors appear on the offending block. For an `optimization` model, which has no components, the screen shows its variables, objective and constraints in place of the graph, in a table view and a diagram view of the same model.
3. **Data:** import CSV or Excel, map columns, fit a distribution to a column.
4. **Experiment:** run length, replications, scenarios, optimization setup.
5. **Run monitor:** progress, live key numbers, cancel.
6. **Results:** plain-language findings first, then charts and tables; export to CSV and PDF. Every results page and exported PDF carries a footer: model name, run id, fidelity label, replications and confidence, engine name and version, and "Simulation results are estimates and carry no warranty."
7. **Settings:** run targets, hardware tier, engine management.

## Hardware tiers

- On first start the service detects cores, memory and graphics, and sets the tier.
- The tier sets defaults: parallel replications now, mesh size limits later.
- Graphics hardware is never required. Both Nvidia and Intel graphics are used when present.
- Low and mid tiers are tested on a machine, container or virtual machine capped to the tier (WSL capping on the development machine is one way).
- How it is detected (AKS-110, proposed default, owner to confirm): `cores` are the logical processors the service process may use; `memory` is the physical memory in bytes (`null` where it cannot be read); `graphics` lists the vendors found (`nvidia`, `intel`, `amd`, or another PCI vendor id as `0x....`), read from `/sys/class/drm` on Linux, and is `null` where it cannot be read (Windows and macOS until the interface needs it). The tier is the highest of `high` (16 cores, 32 GB), `mid` (8 cores, 16 GB) and `low` whose cores and memory the machine both reaches, memory counting as reached at 90% of the nominal size (a 16 GB machine reports less than 16 GiB); below `mid`, or with memory unknown, it is `low`. Graphics does not set the tier in Phase 1, since no Phase 1 engine uses it. The tier found on the first start is stored as `tier` in `settings.json` in the configuration folder, which the Settings screen changes through `PUT /v1/settings` (M9); later starts keep it. `workers` for a run is the lesser of the active tier's cores (4, 8, 16) and the cores the process may use.

## Packaging

- **Linux:** one installable package containing interface, service and Phase 1 engines.
- **Windows:** one installer containing interface, service and Phase 1 engines (proposed default); alternative, an installer plus a prepared WSL image.
- **Engines:** Phase 1 engines are bundled; an environment manager is introduced with the first Phase 3 engine, so later physics engines can be added without reinstalling the app.

### Service rules

- **Local only.** The service listens on `127.0.0.1` and refuses other addresses unless the user turns on remote access.
- **Token.** `Authorization: Bearer <token>`; the token is 32 random bytes, base64url. WebSocket connections authenticate with a first text message `{"token": "..."}` within 5 seconds, else the server closes with code 1008, because webviews cannot set headers. The token is drawn from the operating system's generator (Python's `secrets`), base64url without padding (43 characters), anew at every start; it is a secret, not simulation randomness, so the spec 1 stream scheme does not apply. Every HTTP request needs it, `GET /v1/system` included; a request without it, or with another, gets 401 with E182 and `WWW-Authenticate: Bearer`. The one exception is the interface's own files: a `GET` (or `HEAD`) of a path under `/v1/ui/` needs no token, since a browser loads the page before the page can send one; the files hold no data, and the `Host` check still applies (AKS-119, owner to confirm). A first message that is not that JSON object with the right token, or none within 5 seconds, closes the WebSocket with 1008 and the reason `E182` (AKS-110).
- **Discovery.** The service binds 127.0.0.1 on a port chosen by the operating system and writes `service.json` `{port, token, pid, started}` with mode 0600 in its configuration folder; the launcher, the MCP server and scripts read it. `port` and `pid` are integers, `token` the token text and `started` ISO 8601 UTC ending in `Z`. The file is written before the service answers (through a temporary file and a rename, so a reader never sees half a file) and removed when the service exits, if it still names this service. The configuration folder is `%APPDATA%\lcsim` on Windows, `~/Library/Application Support/lcsim` on macOS and `$XDG_CONFIG_HOME/lcsim` (default `~/.config/lcsim`) elsewhere; the user data folder is `%LOCALAPPDATA%\lcsim`, `~/Library/Application Support/lcsim` and `$XDG_DATA_HOME/lcsim` (default `~/.local/share/lcsim`); `python -m lcsim.service --config-dir ... --data-dir ...` overrides both (AKS-110, proposed default, owner to confirm; `lcsim` is renamed with the package).
- **One service per user.** A second start reads the file, probes `GET /v1/system`, and exits if it answers; otherwise it overwrites the file. The probe sends the file's token, goes to `127.0.0.1` without any proxy, and counts as answered only on a 200 within 2 seconds; the second start then exits with status 0 and prints the running service's port (AKS-110). So that two starts at the same moment cannot both serve, a service holds an exclusive lock on `service.lock` in its configuration folder from before it reads the file until it exits; a start that cannot take the lock is the second start, and it keeps probing for up to 10 seconds while the first is still starting, then exits with status 1 if nothing answers (review of PR #34, owner to confirm). The file is also removed when the service is stopped by a signal (`SIGTERM`, `SIGINT`): uvicorn raises the signal again once it has shut down, which ended the process before the file was removed, so the service takes the signal over, removes the file, and then raises it again, so its exit status still says how it was stopped (AKS-119; M7 "Left").
- **Launcher** (AKS-119, owner to confirm). Until the desktop shell exists (M11), `python -m lcsim.launcher` is how the interface finds and starts the service. It reads `service.json` and probes the service it names, as a second start does; when nothing answers, including when the file is left from a service that has gone, it starts `python -m lcsim.service` detached from itself (a new session on Linux and macOS, a new process group without a console on Windows), its output appended to `service.log` in the configuration folder, and waits up to 30 seconds for `service.json` to name a service that answers. It then opens `http://127.0.0.1:<port>/v1/ui/#token=<token>` in the default browser, or with `--print-url` prints that address instead, for scripts and tests; it exits with status 0 then, and with status 1, naming the log, when no service answers in time. `--config-dir`, `--data-dir`, `--ui-dir` and `--idle-minutes` are passed to a service it starts. A browser started with an address holds the token in its command line for a moment, where another user of the same machine could read it; the desktop shell at M11 opens its own window instead.
- **Interface page** (AKS-119, owner to confirm). The page reads the token from the address's fragment, which a browser never sends to the service, removes the fragment from the address bar, and keeps the token in the tab's session storage, so reloading the tab works while the service runs; the next start's token differs, and its address has another port, so another origin, whose storage is empty. Every request the page makes carries `Authorization: Bearer <token>` and `X-Client: ui`, and every WebSocket sends the token message first. The page's preferences are kept in `settings.json` through `PUT /v1/settings`, not in the browser, whose storage changes with the port.
- **Hardening.** Requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` are rejected; no CORS headers are sent; WebSocket upgrades carrying an `Origin` other than the interface's own are rejected. Rejection is 403 with E183, checked before the token; for a WebSocket the upgrade is refused before it is accepted, which the server answers with 403. An upgrade without an `Origin` (scripts and the MCP server send none) passes this check (AKS-110, owner to confirm). The interface's own origin is the service's, since the service serves the interface (`GET /v1/ui/{path}`): `http://127.0.0.1:<port>` and `http://localhost:<port>`, the host in any letter case; an upgrade with either passes, and any other `Origin` (another port, `https`, another host, `null`) is refused. The desktop shell's origin is added when the shell is built (M11) (AKS-119, owner to confirm).
- **Lifetime** (proposed default, owner to confirm): the service stays up while runs are active or clients are connected and exits after 30 idle minutes; the interface and the MCP server start it on demand. Idle means no run active, no WebSocket open and no HTTP request in progress; the 30 minutes count from the end of the last of these, and at the earliest from when the service starts serving, so the time it takes to start is never idle time (AKS-110, CI on PR #35, AKS-78 open). A run is active from when `POST .../runs` accepts it until it reaches a final state, queued time included (AKS-112).
- **Runs outlive the interface.** Runs are child processes of the service, not of the interface. The service drives each run from a thread of its own and starts its worker as a child process (spec 1 "How the `local` target runs a run"), so a run goes on when the client that started it, or one watching its events, disconnects. Runs do not outlive the service: when the service stops while runs are unfinished, it stops their workers (the cancel grace of spec 1 applies) and marks each `failed` with E191, so no run is left `queued` or `running`; a service that ends without doing so (killed, or the machine stops) leaves that to the next start, which marks them E191 as spec 1 says. The lifetime rule keeps an idle exit from ever stopping a run (AKS-112, owner to confirm).
- **Run queue.** At most `max_concurrent_runs` (default 1, Settings) run at once; others wait in `queued` in arrival order; a run receives `workers` = cores of the active tier. The queue is the service's, across all projects; arrival order is the order in which `POST .../runs` requests were accepted, which are taken one at a time, so a run created first starts first. `workers` is the value `GET /v1/system` reports. The service reads `max_concurrent_runs` (a whole number from 1 to 64), `run_time_limit_s` (a number above 0 and at most 604,800, 7 days; default 600) and `run_memory_limit_bytes` (a whole number from 1 to 2⁶³ − 1, default half the physical memory; spec 4 "Limits") from `settings.json` in the configuration folder when it starts; a key that is absent or holds another value (another kind, a `bool`, or a number out of its range, checked before any conversion so that reading never fails) takes its default, and that is logged (bounds: review of PR #36, owner to confirm). `PUT /v1/settings` writes them (the Settings screen, M9), and they may also be edited in the file; either way a change takes effect at the next start (AKS-112, AKS-119, owner to confirm).
- **Finding thresholds** (AKS-135, owner to confirm). The thresholds of spec 4's finding rules are `finding_thresholds` in `settings.json`, an object with up to five keys: `bottleneck_utilization` and `idle_utilization` (numbers from 0 to 1, defaults 0.85 and 0.30), `relative_half_width` (above 0 and at most 1, default 0.10), `min_time_s` and `min_rate_per_s` (from 0, defaults 60 and 1/3600, the time and rate floors of `not_enough_runs` in seconds and per second). A key that is absent takes its default. The file is read each time `GET .../summary` makes findings, so a change takes effect at the next request without a restart; findings are never stored. A value that is not a number in its range (checked before any conversion, a `bool` refused, as for the run settings), a key that is not one of the five, `finding_thresholds` that is not an object, and a `settings.json` that exists but is not a JSON object the strict reader takes are each refused as a W220 issue (spec 1) at its place in the file, and the default is used for what was refused; the summary and `GET /v1/settings` list these issues in `issues`, and the service logs them. `PUT /v1/settings` writes them (the Settings screen, M9), and they may also be edited in the file (AKS-119).
- **Revision.** Every model write increments an integer `revision`, returned with the model and stored in `project.json`; `PUT .../model` and `POST .../model/edits` accept optional `base_revision`, and a mismatch returns 409 with `{"error": {"code": "E181", ...}, "issues": [], "model": <current>, "revision": N}` and applies nothing. A refused write (400, 409) changes nothing and is not a write. The writes to one project are made one at a time, so two writes stating the same `base_revision` cannot both pass the check. A write first makes both files' final bytes, writes each to a temporary file in the project folder, then renames `model.json` into place and `project.json`, with the new revision, last: that last rename is the commit, and the `model` event is sent only after it. A failure before the commit removes the temporary files, and a failure at it also puts the previous model back, so the revision, the model and the events are unchanged. A service that stops between the two renames leaves the new model under the old revision, which the next write's revision check does not reveal; the rename order was chosen so that the revision never names a model that is not on disk (AKS-111, review of PR #35, owner to confirm).
- **Client header.** Requests may carry `X-Client: ui|mcp|script`, recorded in the run manifest. A request without it counts as `script`; any other value is 400 with E184, checked after the token and before any route runs (AKS-110, owner to confirm).
- **First start.** The interface shows once what the tool does, that results are estimates to support judgement, and where the licence is. That it was shown is remembered as `interface.first_start_seen` in `settings.json`, written with `PUT /v1/settings` when the user presses Continue (AKS-119).
- **Versioned paths.** Every path starts with `/v1`.

Notes on the rows:

- `GET /v1/system`: `{cores, memory, graphics, tier, workers}` as "Hardware tiers" defines them (`memory` in bytes).
- `GET /v1/settings` (AKS-119, owner to confirm): `settings` is `{tier, max_concurrent_runs, run_time_limit_s, run_memory_limit_bytes, finding_thresholds, interface}`, each as the service takes it from `settings.json` now, with its default where the key is absent or holds a value that cannot be used: `tier` the stored tier, or the tier of the detected hardware when none is stored; the three run settings by the rules of "Run queue" (`run_memory_limit_bytes` is `null` when none is stored and physical memory is unknown); `finding_thresholds` with all five keys, by the rules of "Finding thresholds"; `interface` with all seven preferences. `issues` are the W220 issues of the thresholds, as the summary lists them. These are the values the next start (the tier and the run settings) and the next summary (the thresholds) use; `GET /v1/system` reports the tier this start uses. The interface preferences, which the service stores and does not use: `first_start_seen` (`true` or `false`, default `false`), `ask_before_deleting` (`true` or `false`, default `true`), `undo_steps` (a whole number from 100 to 10,000, or `null`, the default, for the tier's recommendation: 200 on `low`, 500 on `mid`, 1,000 on `high`), `theme` (`system`, the default, `light` or `dark`), `text_size` (100, the default, 125, 150, 175 or 200, in percent), `motion` (`system`, the default, which follows the operating system's reduce-motion preference, `full`, `reduced` or `off`) and `colour_blind_charts` (`true` or `false`, default `false`).
- `PUT /v1/settings` (AKS-119, owner to confirm): the body is a JSON object, read as the strict reader reads a file (text that is not JSON, `NaN`, an infinity or text that is not valid Unicode is 400 with E184 at `""`), holding any of the six keys of `settings`. A key given replaces the stored one whole (`finding_thresholds` and `interface` as whole objects, in which a key left out takes its default); a key not given keeps its stored value; a key given as `null` is removed, so its default applies (for `tier`, the next start detects the tier again). Each value is checked by the rules the service reads it with: `tier` is `low`, `mid` or `high`; the run settings have the kinds and ranges of "Run queue"; each threshold the kind and range of "Finding thresholds"; each preference the values above; a `bool` is never a number. A body that is not an object, a key that is not one of the six, five or seven, and a value that cannot be used are each an E184 issue at its JSON Pointer in the body (such as `/finding_thresholds/relative_half_width`), all of them in one 400, and nothing is written. A write keeps any other key `settings.json` holds and replaces the file through a temporary file and a rename, one write at a time; a `settings.json` that cannot be read is replaced, as at first start, and that is logged. The response is the body of `GET /v1/settings` after the write. A change to the thresholds takes effect at the next summary, to the tier and the run settings at the next start, and to the preferences when the interface reads them.
- `GET /v1/ui/{path}` (AKS-119, owner to confirm): a file of the built interface from the folder given by `python -m lcsim.service --ui-dir`, by default `ui/dist` beside the package's source folder `src/lcsim`, which a source checkout has once the interface is built (an installed package has none until packaging names its folder, M11); `/v1/ui/` and a `path` ending in `/` give that folder's `index.html`. `path` is taken as `/`-separated names: one that is empty, `.` or `..`, holds a `\`, a `:` or a control character, or a file that resolves outside the folder (through a link), is refused as not found. A missing folder or file is 404 with E185. The response has the file's media type, `Cache-Control: no-cache`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a `Content-Security-Policy` that lets the page load and connect only to the service itself (`default-src 'self'`, `connect-src 'self'` and the service's `ws://` addresses, inline styles allowed, `frame-ancestors 'none'`), so nothing is fetched from the network at run time (spec 0 principle 6). `HEAD` is answered as `GET`; another method needs the token and is then 405 with E185.
- `GET /v1/engines`: an array, by adapter name, of `{name, version, domains, component_types, hardware, parallel_modes, licence, invocation}`, the adapter's `Capabilities` (spec 1) with `component_types` as the list of type names.
- `GET /v1/schema`: spec 1's static schema (`src/lcsim/model/schema.json`) with one added top-level annotation, `x-component-types`, mapping each installed adapter's component type to the description that `GET /v1/schema/components/{type}` returns. An annotation does not change what the schema accepts, so the composed schema validates exactly as the static one (AKS-110, owner to confirm).
- `GET /v1/schema/components/{type}`: `{type, domain, engine, description, inputs, outputs, outputs_from, settings, metrics}`. `description` is one sentence summarising the type's Behaviour in spec 2's "Block reference"; `outputs_from` names the setting whose entries are the output ports (`routes` for a branch) or is `null`; each setting is `{name, kind, required, ...}` with the keys of the model layer's catalogue that apply to it (`dimension`, `integer`, `many`, `choices`, `refers_to`, `fields`, `keyed_by`, `values`, `required_when`, `minimum`, `exclusive_minimum`, `min_items`, `default`), a time default written as a quantity in seconds (`"86400 s"`). A type no installed adapter has is 404 with E185 (AKS-110).
- `GET /v1/templates` is `[]` and `GET /v1/templates/{tid}` 404 with E185 until the templates arrive (M10).
- `GET /v1/projects`: an array of projects in the order they were registered, each `{id, name, created, layout_version, model_revision, path, available}`; a registered folder whose `project.json` cannot be read, or holds another `id`, is listed with `available` `false` and the other fields `null` except `id` and `path` (AKS-110, owner to confirm). Every JSON file the service reads back from disk (`project.json`, `projects.json`, `settings.json`, and the run files of AKS-112) is read by one strict reader, which takes a file only when the service could write it back: one holding `NaN`, an infinity (also a number such as `1e999`, which reads as one) or text that is not valid Unicode cannot be read, as if it were not JSON (review of PR #36, owner to confirm).
- `POST /v1/projects`: without `template` the project holds `{format_version, meta: {name}, domain: "process", parameters: {}, components: [], connections: [], experiments: [{id: "base", length: "8 h", warmup: "0 s", replications: 30}], run: {target: "local", fidelity: "standard"}}`, which validates with no errors. With `domain` `"optimization"` it holds `{format_version, meta: {name}, domain: "optimization", variables: [], objective: {sense: "maximize", linear: {}}, constraints: [], run: {target: "local", fidelity: "standard"}}`, which also validates with no errors under spec 1 as it stands (the owner's M5 decision to make a model with no variables an error is Phase 1a, AKS-130, and will need this default revisited). `domain` is `"process"` (the default) or `"optimization"` (AKS-110, owner design review 2026-11-06). Projects live under `<user data folder>/projects/<id>/` unless `path` is given (proposed); the service keeps `projects.json` in its configuration folder mapping id to the folder's canonical path: resolved to its real path, absolute, with symbolic links and Windows junctions followed before a `..` after them is applied (as the file system reads `alias/../project`), so `projects.json` stores the folder itself, not the name a client used; the configuration and data folders are made canonical the same way when the service starts (review of PR #34, owner to confirm). `path` must be a full path, on Windows with a drive or a share (`C:\...`, `\\server\share\...`; `\projects` has no drive and names a folder on whichever drive is current), else 400 with E184; it must name a folder that does not exist or is empty, else 400 with E186. `name` is non-empty text. A `template` is 404 with E185 until M10. The response is the project as `GET /v1/projects` lists it; the new folder holds `project.json`, `model.json`, `data/` and `runs/`, with `model_revision` 0 and `layout_version` 1 (`index.sqlite` is made when the service first uses the project's runs, AKS-112). Proposed defaults, owner to confirm.
- `POST /v1/projects/open`: `path` must be a full path, as for `POST /v1/projects` (E184); a folder that does not exist is 404 with E185, and one without a readable `project.json` holding the five fields is 400 with E186. Opening a project already registered at the same folder, under any name for it (the same canonical path, or `os.path.samefile` when both exist), returns it unchanged; one whose `id` is registered at another folder that still holds that project is 400 with E186 (a copied folder keeps its id), and otherwise the registration moves to the new path (AKS-110, owner to confirm).
- `GET .../model`: `{model, revision}`, the model as `model.json` holds it. Every model the service takes in passes one admission gate: it must become the exact bytes the service writes (JSON without `NaN` or infinities, in strict UTF-8), so a number JSON cannot hold (`NaN`, `Infinity`, or one such as `1e400` that reads as an infinity) or text that is not valid Unicode (a lone surrogate such as `"\ud800"`) is refused, whatever else loading reports. A project whose `project.json` cannot be read, or whose `model.json` is not JSON or is not admitted, is 400 with E186; for a model not admitted `issues` holds an E100 at the value's place, and edits are refused the same way before anything moves. The same values in a request are refused where they arrive: E100 in a `PUT` body, E184 in an edit's field or another request field, and E180 at `/edits` for a batch whose result is not admitted, so no path leads to a 500. Every response body is JSON with the characters outside ASCII escaped (AKS-111, review of PR #35, owner to confirm).
- `PUT .../model`: the body is the model file itself, read as spec 1 "Validation" reads a file (so a key written twice, `NaN` or text that is not JSON is E100), whatever its content type; a number JSON cannot hold once read, such as `1e400`, which reads as infinity, is also E100, at its place, since it could not be saved. Since the body is the file, `base_revision` is the query parameter `?base_revision=N`, a whole number (otherwise 400 with E184). What is saved is the parsed file, written as JSON indented by two spaces. A schema failure is 400 with `error.code` the code of its first issue (E100 or E101) and every schema issue in `issues`. The response is `{model, revision, issues}`, where `issues` are those of loading the saved file (spec 1: the meaning pass and its warnings), not the adapter's `validate` (AKS-111, owner to confirm).
- `POST .../model/edits`: the body is `{edits, base_revision?}`; the response is `{model, revision, issues}` as for `PUT`. When `model.json` on disk does not pass the schema pass (it was changed outside the service), edits are refused with 400 and E186, its schema issues in `issues`, until a whole model is written with `PUT` (AKS-111, owner to confirm).
- `POST .../validate`: takes no body and returns `{revision, issues}` for the saved model: the issues of the schema pass, then of the meaning pass (spec 1 loading), then of the adapter's `validate`, which runs only when the first two find no error, since it needs a model that loads. The admission gate runs first: a saved file it refuses gives its E100 issue alone, and the adapter is not called. `empirical` `data` references are checked against the project's column index ("Project folder"; AKS-111, AKS-113, owner to confirm).
- `GET .../events`: after the token message, the stream first sends `{"type": "model", "revision": N, "client": null}` with the current revision, so a client knows where it starts, then one `model` event per write in revision order, with `client` the write's `X-Client` (`script` when absent). A project id the service does not know closes the connection with 1008 and the reason `E185`, after the token. `run` events are `{"type": "run", "run_id", "state"}`: one with `queued` when a run is created, then one for every state change, in the order of the changes (AKS-111, AKS-112, owner to confirm).
- Data (AKS-113, owner to confirm). `POST .../data` takes `multipart/form-data` with the part `file`, the file itself, and optionally the part `units`, a JSON object mapping column names to a Phase 1 time unit (`s`, `min`, `h`, `d`) or `null`; another part, a second file, a `units` that is not such an object, a unit for a column the file does not have or for one whose `type` is not `number` is 400 with E184 at `/file` or `/units/<column>`. The file's name is the part's file name, never taken as a path (the multipart parser, `python-multipart`, keeps only the last part of a Windows path such as `C:\data\a.csv` or `\\server\a.csv`, which old browsers sent): 1 to 100 characters of ASCII letters, digits, space, `.`, `_` and `-`, starting with a letter or a digit and ending in `.csv` or `.xlsx` (any case), whose part before the first `.` is not a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, any case); otherwise 400 with E184 at `/file`. A name already in the index is imported again, replacing that file and its entry in place; a name that differs from one in the index only in letter case is 400 with E184, since Windows takes them as one file. The request may be at most 64 MiB plus 64 KiB for the form, checked from `Content-Length` and while it is read; a larger one, or a file of more than 64 MiB, is 400 with E189. A CSV file is UTF-8 (with or without a byte order mark), comma separated with `"` quotes; an `.xlsx` file is read from its first worksheet, formulas by their saved values, from at most 512 MiB unpacked. The first row names the columns: each name is stripped of surrounding spaces and must be non-empty, not a number, at most 200 characters and unlike the others. Every later row is a record; a row whose cells are all empty is skipped, a shorter row has empty cells at its end, and a row with a non-empty cell beyond the header is E189. At most 1,048,576 records and 10,000,000 cells. A cell is a number when it is a finite number (in a CSV, text that follows spec 1's number grammar once stripped), empty when it is empty or only spaces, and text otherwise (an Excel date or a `TRUE` is text). A column's `type` is `number` (at least one number and no text), `text` (at least one text cell) or `empty`. A file that is not UTF-8 text or an Excel workbook (a password-protected workbook is not one), that cannot be read, has no header row or breaks these rules is 400 with E189, and nothing is saved. The response is the file as `GET .../data` lists it, with `preview`: its first 10 records as arrays in column order, each cell a number, text or `null`. The file and its index entry are saved together (each written to a temporary file in `data/`, the file renamed into place, then the index, which commits; a failure at the commit puts the previous file back) while no write of the project's model is under way; validation, a model write and a run's creation read the index and hash the files the same way, so none of them ever meets half an import.
- `GET .../data`: an array of the imported files in the order first imported, each `{name, format, sheet, size, sha256, imported, rows, columns}`: `format` is `csv` or `xlsx`, `sheet` the worksheet read (`null` for a CSV), `size` the file's bytes, `sha256` their hash at import, `imported` ISO 8601 UTC ending in `Z`, `rows` the number of records, and `columns` an array of `{name, type, unit, largest}` in file order, `largest` being a `number` column's largest absolute value as the file holds it (`null` for another type), from which validation tells whether every value is a finite time (spec 1 "Distributions"; review of PR #37).
- `DELETE .../data/{file}`: removes the file's index entry (the commit) and then the file, and returns the remaining files as `GET .../data` lists them; a name not in the index is 404 with E185. A file the model still names may be removed: validation then reports E162 at each reference, and runs already created keep their snapshots.
- `POST .../data/{file}/fit`: the body is `{column}`, text; a name not in the index is 404 with E185, a column the file does not have is 400 with E184 at `/column`, and a column whose `type` is not `number`, or a file now missing or changed since its import, is 400 with E189. The response is `{file, column, unit, values, score, candidates, histogram}`: `values` is the number of values fitted, `score` is `"ks"`, and `candidates` lists, best first (ties in spec 1 order), `{distribution, score}`: `distribution` a spec 1 distribution object, its time fields as quantities in the column's unit (plain numbers when the column has none; a Weibull `shape` is always one), so `set_setting` can take it as it is, and `score` the Kolmogorov–Smirnov statistic of the fit, from 0 (best) to 1. A column whose values are all equal gives `constant` alone; otherwise the candidates are `exponential` (values not negative, mean above zero), `uniform`, `triangular`, `normal`, `lognormal` and `weibull` (values above zero) as far as each fits, by maximum likelihood; `empirical` is not a candidate, since the column itself is written as a `data` reference. A family whose fit fails is left out, and every candidate, `constant` included, passes one gate: it is loaded as the distribution of a time setting by the model layer, and left out if loading reports an error for it (a time field that is not a finite number of seconds, E141; fields that must agree, E160), so every candidate returned is one the model takes as it is (review of PR #37). `histogram` is `{edges, counts}`, the column's values as the file holds them (in the column's unit) counted in bins of equal width, for the Data screen's chart (AKS-120, owner to confirm): with n values, there are k = min(50, ⌈log₂ n⌉ + 1) bins (Sturges' rule) from the smallest value to the largest; `counts` holds k whole numbers that add up to n, a bin holding the values from its lower edge up to but not including its upper edge, the last bin also its upper edge; `edges` holds the k + 1 edges, the first the smallest value and the last the largest; a column whose values are all equal has one bin, both of whose edges are that value. The edges are worked out in units of the largest absolute value, as the fit is, so every edge is a finite number.
- `POST .../runs`: `experiment_id` is required for a `process` model and must be absent for an `optimization` model, which has no experiments (400 otherwise). `target` overrides the file's `run.target` for this run and is recorded in the manifest; 422 when the model has errors; E172 with 422 when the target is unavailable. How it is checked (AKS-112, owner to confirm): the body is `{experiment_id?, target?}`, both text when present, and a request without a body is `{}`; another shape is 400 with E184. The run is made from the bytes of `model.json` as saved, read while no write of the model is under way. In order: loading the file (its errors: 422, `issues` listing every error and warning, `error.code` the first error's code); the target, the request's when given, else the file's (anything but `local` is 422 with E172, at `/target` for the request's); the experiment (none for a `process` model, one for an `optimization` model, or one the model does not have: 400 with E184 at `/experiment_id`); the adapter's `validate` and the fidelity check (422 as for loading). An unknown project is 404 with E185, one that cannot be read 400 with E186. Nothing is created when a check fails. The response is 202 with `{run_id}`, and the run waits in the run queue.
- A run as the run endpoints show it (AKS-112, owner to confirm): `{run_id, project_id, experiment_id, state, fraction, message, created, started, ended, error}`, the manifest's fields (spec 1) with `error` `null` unless the run failed, and `message` the latest progress message, `""` when none is known (no report yet, or the run belongs to an earlier start of the service). A run id is found through `projects.json` and each project's `index.sqlite` (spec 1); an id not of the `run_id` form, not in the index of a registered project, or whose `manifest.json` cannot be read is 404 with E185.
- `GET .../runs`: an array of runs in the order they were accepted.
- `POST .../cancel`: a `queued` run moves to `cancelled` at once; for a `running` run the cancel is accepted and the run stays `running` until its worker stops (spec 1 "Cancel"), a repeat being accepted the same way; the response is the run. A run that has ended is 409 with E188 (AKS-112, owner to confirm).
- `GET .../summary`: `{summary, findings, issues}`: `summary` as `summary.json` holds it; `findings` the findings of spec 4 "Finding rules" (`lcsim.findings.find`), each `{rule, severity, component, scenario, text, evidence}`, in the rules' fixed order, made at the request from the run folder's `summary.json` and `model.json` (the model that ran, never the project's current model, which may have changed since) at the thresholds of "Service rules", Finding thresholds; and `issues` the W220 issues of reading those thresholds, usually empty (AKS-135). The run folder's model is loaded as the run loaded it except that its `data` references are not checked against the project's data again (the project's files may have changed or gone since, and the rules read no data); the manifest's `seed` stands in for one the file leaves out. A run that is not `done` is 409 with E188; a `summary.json` the strict reader refuses, or one the finding rules cannot read (JSON of another layout), and a run folder `model.json` that cannot be read or loaded are 404 with E185 (AKS-112, review of PR #36, AKS-135, owner to confirm).
- `GET .../tables/{name}`: `format` is `json` when absent; another value is 400 with E184. `json` gives an array with one object per row, keyed by the table's columns, a NaN value as `null`; `csv` gives `text/csv` in UTF-8 with a header row, a NaN value as an empty field and floats written as the shortest text that reads back to the same float. A name other than `replications` and `timeseries`, a table the run does not have (an optimization run has none) or one that cannot be read is 404 with E185; a run that is not `done` is 409 with E188 (AKS-112, owner to confirm).

`tests/service/test_routes.py` lists the application's routes and asserts the set equals this table, both ways; each row also has at least one request test. How it is checked (AKS-114, owner to confirm): the test reads this table from this file when it runs; the application's routes are listed with a WebSocket route as `GET`, as the table writes it. A request test is a request in `tests/service/` that the service's router matched to the row's route with the row's method, so a request refused by the hardening rules (401, 403, a bad `X-Client`), one to an unknown path and one with another method do not count; every test client in `tests/service/` records the routes its requests reach, and the last test of the session asserts that every row was reached (a session that runs only part of `tests/service/` makes that record in a separate run of all of it).

### Model edits

An edit is rejected only when it cannot be applied: unknown or duplicate component id, unknown type, an unknown parameter or experiment named by `remove_parameter`, `remove_experiment`, `set_scenario` or `remove_scenario`, a new parameter without `value` and `type`, a `path` whose parent does not exist. Rejections are issue objects with code E180 and `path` `/edits/<n>`; the batch is then not applied and the response is 400. A batch that applies is saved even if validation then reports errors; the response is 200 with the model, its revision and the issues. `PUT .../model` follows the same principle: the file is saved when it passes the schema pass, and the response carries the meaning-pass issues; a schema failure (E100, E101) returns 400 with those issues and saves nothing. 422 is returned only by `POST .../runs`. The interface and the MCP server both use this one mechanism.

How edits are written and applied (AKS-111, owner to confirm):

- **Shape.** Each edit is an object whose key `edit` names its kind, with the fields of the table and no others. `id`, `new_id`, `type`, `from`, `to` and `experiment_id` are text; `params`, `ui` and `set` are objects; `path` is a JSON Pointer (RFC 6901) as text; `label` is text or `null`; `value`, and the fields of `set_parameter` and `set_experiment` other than `id`, take any JSON value. No field may hold a number JSON cannot hold once read (such as `1e400`), or text that is not valid Unicode. `edits` holds at least one edit. An edit of another shape is 400 with E184, one issue per problem at `/edits/<n>` or `/edits/<n>/<field>`, and nothing is applied: these problems do not depend on the model.
- **Order.** The edits are applied in order, each to the model the earlier ones left. The first edit that cannot be applied is reported, as one E180 issue. An `id` names the first component, experiment or scenario with that id. Since a batch may pass through states the schema pass would refuse, an edit meets the model in any shape: a list or object it must change is created when absent and cannot be applied when it is of another kind (E180), what it only reads is skipped where it cannot be read, and an edit is always applied or rejected with E180, never answered with 500 (review of PR #35).
- **Pointers.** In a `path`, an array is addressed by an index without leading zeros; `set_setting` and `set_path` replace the entry at an index, and append at `-` or at the array's length. A `path` of `""` names no setting or key and cannot be applied. `set_path` and `remove_path` reach `/meta`, `/run`, `/objectives`, `/constraints` and `/experiments/<n>/search`, and in an `optimization` model `/variables` and `/objective`, and what lies below them; another `path` cannot be applied. `remove_path` cannot be applied to a `path` that does not exist.
- **Schema.** A batch whose result would not pass the schema pass cannot be applied, so `model.json` always passes it: E180 is reported at the edit after the last one that left the model passing, and its message gives the first schema issue. Examples: `set_path` of `/meta/name` to a number, `remove_path` of `/meta`, `connect` or `set_experiment` in an `optimization` model.
- **Names.** `set_scenario` cannot be applied when its `set` names a parameter the model does not have, and `remove_scenario` when the experiment has no scenario of that `id`. `connect` and `disconnect` name ports, not component ids: a `connect` to an unknown component or port is applied and the meaning pass reports it (E130), and a `disconnect` of a port with no connection changes nothing. A `connect` leaves exactly one connection from its `from`. `remove_component` removes every connection whose `from` or `to` names the component; settings and metrics that still name it are reported by the meaning pass (E124, E174). `rename_component` rewrites the component part of connection ends, every setting its type declares as naming a component (`pool`, `target`) that names it, and every objective and constraint `metric` that starts with `<id>.`; a `new_id` that another component has cannot be applied. `remove_parameter` treats as references a `{"$param": id}` in any component setting, a scenario `set` key and a `search.variables` entry. `set_parameter` and `set_experiment` set fields and never remove one.
- **Domain.** No edit changes `domain`. A project's domain is chosen when it is created (`domain` on `POST /v1/projects`) and changes only by writing a whole model with `PUT .../model`, which closes the gap the owner design review left for M6.

### Status codes and errors

| Code | When |
| --- | --- |
| 200 | Success |
| 202 | Run accepted |
| 400 | Request malformed (E184); an edit that cannot be applied (E180); a model file that fails the schema pass (E100, E101); a project folder that cannot be used (E186); a data file that cannot be imported or a column that cannot be fitted (E189) |
| 401 | Token missing or wrong |
| 404 | Project, run, table, data file or interface file not found |
| 409 | Action not allowed in the run's current state (E188), or the model revision has changed (E181) |
| 422 | `POST .../runs` only: the model has validation errors; the body lists the issues |
| 403 | Refused by the hardening rules: `Host` or WebSocket `Origin` not allowed (E183) |
| 405 | Method not allowed on a documented path (E185) |
| 500 | The service failed; the details are in its log, never in the body (E187) |

Every error body is `{"error": {"code", "message"}, "issues": [...]}`, where issues use the spec 1 issue object. `error.code` is a spec 1 code (AKS-110, owner to confirm): E182 for 401, E183 for 403, E184 for a malformed request (body not JSON, a field missing, unknown or of the wrong kind, a bad `X-Client`), E185 for an unknown project, template, component type or path (404) or method (405), E186 for a project folder that cannot be used (400), E187 for 500, and the codes the rows above name: E180 at `/edits/<n>` and the E100 or E101 issues of a `PUT` are listed in `issues`, and a 409 with E181 has none (AKS-111, owner to confirm); E188 for a 409 of the run endpoints, and for a 422 the first error's code (E172 for a target), its issues listed (AKS-112, owner to confirm); E189 for a data file or column that cannot be used, its `issues` one issue whose `path` is `/file` or `/column` (AKS-113, owner to confirm). For E184 `issues` holds one issue per problem, its `path` a JSON Pointer into the request body as E180's `/edits/<n>` is; otherwise `issues` is empty unless the row says it lists them.

### Progress events

```json
{"type": "progress", "fraction": 0.4, "message": "Scenario 1 of 2, replication 12 of 30"}
{"type": "metrics", "scenario": "default", "values": {"till.wait.mean": 268.1}}
{"type": "state", "state": "done"}
```

On connection the stream first sends `{"type": "state", ...}` and the latest `progress` event, then live events; after a terminal state the server sends it and closes. A client may connect at any time, including after `done`.

How the stream is built (AKS-112, owner to confirm): after the token message (as for every WebSocket), a run that cannot be found closes the connection with 1008 and the reason `E185`. The first two events are the run's state and progress at one instant, so no change is missed or sent twice: an event that changed them before that instant is not sent, and every later one is. `progress` is `{"type": "progress", "fraction", "message"}` with the manifest's `fraction` and `message` as "A run as the run endpoints show it" defines it; live `progress` events follow every report of the adapter (for a search, the weighted fraction and the "Search, candidate n" or "Confirmation, candidate n" message of spec 2). After the final state the server closes with 1000; a run already final sends its state and progress and closes. A final state is made visible (the run endpoints, this stream, the project's `run` events) only once the run has finished on disk and freed its queue place (spec 1 "Finishing order"); until then the run endpoints show the run as last published, so a stream opened while the manifest is already final starts from `running` and then sends the final state, once (CI on PR #36, owner to confirm). `metrics` events are sent only for an adapter that reports live metrics, and no Phase 1 adapter does, so none is sent yet. What the client sends after the token is ignored.

### Project folder

```text
<project>/
  project.json    id, name, created, layout_version, model_revision
  model.json      the current model
  data/           imported files, unchanged, plus a column index
  runs/           one folder per run, as in spec 1
  index.sqlite    run index, rebuilt from runs/ if missing
```

`index.sqlite` is a cache: the run ids of `runs/` in the order the runs were accepted, with `created` and `experiment_id`. The manifests are the source of truth, so a run's state is always read from its `manifest.json`. When the service first uses a project's runs (on start for every registered project), it rebuilds the index if it is missing or cannot be read (in the order of `created`, then `run_id`), adds the run folders it lacks and drops those that are gone (AKS-112, owner to confirm).

`project.json` holds `{id, name, created, layout_version, model_revision}`; `id` is a UUID4 string and is `pid`. The model's own `format_version` is inside `model.json`. `created` is ISO 8601 UTC ending in `Z`; `layout_version` is 1 for the layout above; `model_revision` is 0 for a new project (AKS-110). Every number the service reads from disk and then uses has a declared kind and range (review of PR #36, owner to confirm): `layout_version` is a whole number from 1 and `model_revision` one from 0, each at most 2⁶³ − 1; a `bool`, a float, text or a value out of range makes `project.json` unreadable (E186). A write that would take the revision past 2⁶³ − 1 is 400 with E186 and saves nothing.

`data/` holds each imported file under its name, unchanged, and the column index `data/index.json`: `{"index_version": 1, "files": [...]}`, each file as `GET .../data` lists it. The index is read by the strict reader, with every number of a declared kind and range (`size` and `rows` whole numbers from 0 to 2⁶³ − 1, `sha256` 64 lower-case hexadecimal digits, `type` one of the three words, `unit` a Phase 1 time unit or `null`, `largest` a finite number from 0 for a `number` column and `null` otherwise); an index that cannot be read, or holds a name the naming rule refuses, is taken as empty, so every `data` reference is E162 until the files are imported again, which writes a new index (AKS-113, owner to confirm).

The folder is plain files so it can be copied, zipped or put under version control. The project folder, not the model file alone, is the unit to share when a model uses imported data; the Results screen's export produces a zip of the project folder.

### Canvas behaviour

These are functional rules. Visual design is covered by the checklist below.

- **Single source.** The canvas shows the model file and nothing else. Every canvas action is one or more model edits.
- **Add.** Dragging a block from the palette adds a component with a generated id, such as `server_2`, and default settings. How (AKS-136, owner to confirm): the id is `<type>_<n>`, `n` one more than the highest number any component id of that form holds (so a deleted block's id is not given to the next, and a renamed block's is not taken); the edit is `add_component` with `params` `{}` and `ui` `{"x", "y"}` at the drop point. A setting the type gives a default is left out, since an absent setting takes its default (spec 1), and a required setting with no default is left out too, so validation reports it (E122) until the user fills it in; a block therefore writes only what the model needs.
- **Connect.** Dragging from an output port to an input port sends `connect`. Dragging from an output port that is already connected replaces its connection.
- **Delete.** Removes the selection and its connections, after a confirmation the user can turn off in Settings (on by default).
- **Undo and redo.** At least 100 steps, covering every model edit. Each step stores the model as it was; undo and redo write the stored model with `PUT .../model` and `base_revision`, because some edits (such as `set_setting` creating a new key) have no inverse edit. The number of steps is Settings' `undo_steps`, or the tier's recommendation when it is `null` (AKS-136).
- **Clearing.** No edit removes a component setting or a parameter's `min` or `max`, so clearing an optional one writes the whole model without it, with `PUT .../model` and `base_revision`, as undo does; it is one undo step (AKS-136, owner to confirm).
- **Save.** Automatic after every edit. There is no save button. One write at a time: while a write (or a reload of the model) awaits its answer, the canvas takes no other change, so every action is computed from the model shown, which holds every accepted write; its model-changing controls are unavailable but keep the focus, a text field's commit is refused, the field shows the saved value again and a notice says the change was not saved because the canvas was saving and to make it again (nothing is kept or sent later), and the save state shows "Saving…" (AKS-136, review of PR #45, owner to confirm). While a write gets no answer from the service, the canvas is read-only and the same write is retried every 2 seconds (owner design review, choice 8; AKS-136).
- **Validate.** Runs half a second after the last edit. Issues appear as a marker on the block and in a list; selecting a list entry selects the block.
- **Run.** Disabled while errors exist, or while a write or validation is pending, with the reason shown (owner design review, choice 9; AKS-136).
- **Rename.** Changing a component's id updates its connections and any references to its metrics. The side panel's Id field sends `rename_component`; a block's label is set with `set_label` (AKS-136).
- **External edits.** The canvas sends `base_revision` on every write and, on a `model` event whose revision it did not produce, reloads the model and shows a one-line notice naming the client. The reload clears the undo and redo history, so an undo cannot silently revert another client's change. The canvas marks what the other client added, changed or removed, and the user can accept or reject each change; a rejection is an ordinary write of the model with that item restored, sent with `PUT .../model` and `base_revision`. How (AKS-137, review of PR #46, owner to confirm): a 409 with E181 is an outside change too, and its notice says the canvas's last change was not saved. The notice names each client whose `model` event lies between the revision shown and the one read ("by an assistant (mcp)", "by a script (script)", "in another window (ui)", "by another program" when none is known), and stays until dismissed or replaced. The canvas keeps one baseline: the model shown before the first outside change not yet reviewed, with the user's own writes since taken into it, so they are never marked. The marks are always the comparison of the baseline with the model shown, item by item by stable id: components by `id`, connections by `from`, parameters by name, experiments, `objectives`, variables and constraints by `id`, an `optimization` model's `objective` as one item, and every other top-level key (`meta`, `run`, ...) as one item; a list that is not a list of objects with distinct ids is one item; key order and list order are not changes; a rename is a removal and an addition. A later outside change is compared with the same baseline, so changes compose without being tracked one by one, and an item the other client puts back is no longer marked. Accept takes that item as shown into the baseline and writes nothing; Accept all makes the model shown the baseline. Reject writes the model shown with that item as in the baseline (a removed one put back at its place in its list), one undo step; Reject all writes the baseline, one undo step. Accept and Reject follow the Save rule: while a write awaits its answer they are unavailable. Names a model holds (parameter, decision and coefficient names, types, ports) are looked up as own properties only, so `constructor` or `__proto__` is an ordinary name.
- **Optimization models.** The Canvas screen of an `optimization` model has a Table view and a Diagram view of the same model, with a switch; the Table view is shown first. In the Table view the variables are "Decisions" (name, kind, lower and upper bound), the objective is the "Goal" (maximize or minimize, and one coefficient per decision) and the constraints are "Limits" (name, one coefficient per decision, at most, at least or exactly, and the limit). Every change is one batch of `set_path` and `remove_path` edits on `/variables`, `/objective` and `/constraints`, one undo step, under the Save rule. Emptying an optional field (a bound, a coefficient) removes it with `remove_path`; a number is sent as a number when it follows spec 1's number grammar and as typed otherwise. Renaming a decision also renames its coefficients in the goal and the limits, in the same batch, unless another decision has the new name (the service then reports the duplicate); removing one removes its coefficients with it. A new decision is `{"id": "decision_<n>", "type": "continuous"}` and a new limit `{"id": "limit_<n>", "linear": {}, "op": "<=", "rhs": 0}` (the schema needs `op` and `rhs`), `n` as in Add. A field shows the issues whose `path` names it. The Diagram view draws each decision as a card on the left and the goal and each limit as a card on the right, with a line from a decision to each card whose coefficients name it, labelled with the coefficient; the layout is computed and nothing about it is stored, and choosing a card opens its row in the Table view. The screen has no experiment picker. Spec 1's variables hold no unit or icon, so a decision's name is its id (AKS-137, owner to confirm).
- **Try a change.** Beside a number or time field of the side panel (also one inside a distribution, not a whole distribution) "Try a change" asks the value to try and a name for the option, and sends one batch of edits, one undo step, under the Save rule, built from the model shown (`docs/design/canvas-interactions.md` "Trying a change"): `set_parameter` creating a parameter named `<block>_<field path joined by _>` (with `_2`, `_3` when taken) holding the field's value, of type `quantity` for a time, `integer` for a whole-number setting and `number` otherwise; `set_setting` linking the field to it at the field itself; `set_scenario` adding `baseline` (or `baseline_2`, ...) with an empty `set` when the experiment chosen in the top bar has no scenarios of its own; and `set_scenario` adding the option, its id the name typed made an identifier (lower case, other characters as `_`, `option_` before one that does not start with a letter, at most 64 characters), never one already taken or `default`, its `set` giving the parameter the value tried (as typed for a `quantity`, a number by spec 1's number grammar otherwise). A field already linked to a parameter adds only the scenarios. The form closes whenever the model shown changes; with no experiment it says so and sends nothing (AKS-120, owner to confirm).
- **Data and Experiment screens.** These screens change the model through the same session as the canvas, so the Save and External edits rules hold on them too: one write at a time, every control that changes the model unavailable while a write or reload awaits its answer, a draft (a typed id, a "Use for" choice, the waiting question's answer) never outliving a change to the model shown, an outside change reloading the model with its notice and the list of changes to review, and Undo and Redo in the top bar. The Experiment screen sets an experiment's fields with `set_experiment`, clearing an optional one by writing the whole model without it (no edit removes a field); its scenarios with `set_scenario` (one column per parameter, an empty cell leaving the parameter out of `set`) and `remove_scenario`; `objectives` and `constraints` with `set_path` and `remove_path`, renaming an objective also renaming the `search.objective` that names it in the same batch unless another objective has the new name; and an experiment's `search` with `set_path` and `remove_path` on `/experiments/<n>/search` (turning it on writes `{"objective": <the first objective's id, or "">}`). An `optimization` model has no experiments, which the screen says. The Data screen uses the four data routes, and writes a block's distribution setting with `set_setting`: the candidate chosen as the fit returned it, or `{"dist": "empirical", "data": {"file", "column"}}`; before a server's `service` or a delay's `time` it asks "Does this column include time spent waiting?", setting it on No and, after a warning, on "Use it anyway" for Yes or Not sure. A number column's unit is chosen by importing the file again with `units`, which needs the file picked in that window; the preview of 10 records is the import's answer, so it is shown for files imported in that window. After an import or a removal the model is validated again, since `data` references read the column index (AKS-120, owner to confirm).
- **References.** Blocks without ports (`resource_pool`, `schedule`, `failure`) are placed like any block. Their `pool` and `target` settings are drawn as reference lines, which are not connections and differ by kind in pattern, icon and word; they are set in the side panel with `set_setting`.

### Performance targets

All proposed, to be measured on the low tier (proposed; measured per the Build guide protocol, confirmed by the owner):

- Service ready within 5 seconds of start.
- Canvas stays responsive with 200 components: an end-to-end test adds 200 components by API and selecting a block paints within 100 ms (proposed).
- Validation of a 200-component model within 200 milliseconds.
- Service uses under 300 MB of memory when idle.

How the three service targets are measured (AKS-114, owner to confirm; `tests/perf/test_service.py`): "ready" is the first 200 from `GET /v1/system`, timed from just before `python -m lcsim.service` is started; validation is `POST .../validate` of a model of 200 components (a source, 198 servers in a line and a sink) timed from request to response over loopback HTTP, the largest of 20 calls; idle memory is the resident memory of the service and every process it started, after 5 seconds with no request, both just after the start and after a run has ended, with 300 MB read as 300,000,000 bytes. Measured at M6 on 4 cores (`docs/research/perf-M6.md`; not the low tier, owner to confirm): on Python 3.13, ready in at most 1.4 seconds, validation in at most 0.16 seconds (median 0.08), idle at 178 MiB after the start and 249 MiB (261 MB) after a run; on Python 3.11 within 5% of these, idle at 257 MiB (269 MB) after a run.
