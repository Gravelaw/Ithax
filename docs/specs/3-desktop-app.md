## Scope

- **In:** the engine service, its API, the interface, project storage, data import, packaging, hardware tiers.
- **Out:** the model format (spec 1), engines (specs 2, 5, 6), templates and assistant tools (spec 4).

## Architecture

| Part | Role | Proposed technology |
| --- | --- | --- |
| Engine service | Validates models, schedules runs, hosts engine adapters, serves results | Python with FastAPI 0.162.1 or later, served by uvicorn 0.54.0 or later with websockets (never `uvicorn[standard]`, whose uvloop has no Windows build); confirmed 2026-11-07 (`docs/research/spec-3-service-framework-check.md`; licences in `docs/DECISIONS.md`) |
| API | The only way in: HTTP for requests, WebSocket for live progress | Local address only by default |
| Interface | Canvas, forms, charts | React with React Flow (`@xyflow/react`), packaged as a desktop app with Tauri 2, version 2.11.1 or later (confirmed 2026-11-06, re-checked 2026-11-09; the shell in `desktop/` is built on Linux with 2.12.5 since M11, "Service rules", Desktop shell; licences in `docs/DECISIONS.md`) |
| Storage | One folder per project: model file, imported data, runs | Files, plus SQLite as a run index |

On Linux both parts run natively. Phase 1 is packaged and tested on Linux only (owner decision B4, 2026-11-09); the Windows version is deferred, and the Phase 1 review sets its phase. When it comes, both parts run natively on Windows (proposed default from the review, owner to confirm): every Phase 1 dependency ships Windows wheels or is pure Python (highspy, numpy, scipy, pyarrow, pyomo, simpy, optuna, pint, fastapi; PyPI file lists read on 2026-11-05), while WSL costs an administrator install, a restart and by default half the memory of a low-tier machine. A WSL path is added in Phase 3 for engines without Windows builds. Service code stays platform-neutral (no fork-only process code, no Linux-only paths), so the Windows version needs no rewrite (B4).

## API

| Endpoint | Purpose |
| --- | --- |
| `/projects` | Create, open, list |
| `/models` | Read and write the model file |
| `/validate` | Run both validation passes |
| `/runs` | Start, cancel, list; `/runs/{id}/events` streams progress |
| `/results` | Summary and tables (fields arrive with spec 6) |

The interface uses no private channel. Anything it can do, a script or an assistant can do through the same API.

## Screens

1. **Home:** recent projects, template gallery, Learn or Build entry (Build mode form as in spec 4).
2. **Canvas:** drag blocks from a palette, connect them, edit properties in a side panel. Validation errors appear on the offending block. For an `optimization` model, which has no components, the screen shows its variables, objective and constraints in place of the graph, in a table view and a diagram view of the same model.
3. **Data:** import CSV or Excel, map columns, fit a distribution to a column.
4. **Experiment:** run length, replications, scenarios, optimization setup.
5. **Run monitor:** progress, live key numbers, cancel.
6. **Results:** plain-language findings first, then charts and tables; export to CSV and PDF. Every results page and exported PDF carries a footer: model name, run id, fidelity label, replications and confidence, engine name and version, and "Simulation results are estimates and carry no warranty."
7. **Settings:** run targets, hardware tier, engine management, the service's idle timeout.

How Home leads to the two modes (AKS-124, owner to confirm; the behaviour of each mode is spec 4 "Learn and Build modes" and "Build mode"):

- **Home.** The gallery lists every template of `GET /v1/templates` as a card with its title, summary, audience and estimated minutes, and "Start the lesson", which starts Learn mode on that template. Learn orders the gallery students first ("Students", "Both", "Business") and moves the focus to it; Build opens the Build form at `#/build`. Build is unavailable, with its reason, when the service lists none of the Build form's templates. "New empty project" and "Open a project folder" stay as they are.
- **The Build form** is a screen of its own (`#/build`, the navigation rail showing Home as current; the top bar says "Build a model"), so the browser's Back leaves it. It sends nothing until Continue.
- **Learn mode** is played on the Canvas screen of the project made from the template: the Canvas of a `process` model, the Table and Diagram views of an `optimization` model, with a step card; the exercise's run opens the Run monitor, and Results of that run show the prediction and the explanation first. The lesson is held by the interface only while it is open (spec 4); it adds no route and no request beyond the documented ones (`GET /v1/templates/{tid}`, `POST /v1/projects`, and the Canvas's own).

## Hardware tiers

- On first start the service detects cores, memory and graphics, and sets the tier.
- The tier sets defaults: parallel replications now, mesh size limits later.
- Graphics hardware is never required. Both Nvidia and Intel graphics are used when present.
- Low and mid tiers are tested on a machine, container or virtual machine capped to the tier (WSL capping on the development machine is one way).
- How it is detected (AKS-110, proposed default, owner to confirm): `cores` are the logical processors the service process may use; `memory` is the physical memory in bytes (`null` where it cannot be read); `graphics` lists the vendors found (`nvidia`, `intel`, `amd`, or another PCI vendor id as `0x....`), read from `/sys/class/drm` on Linux, and is `null` where it cannot be read (Windows and macOS until the interface needs it). The tier is the highest of `high` (16 cores, 32 GB), `mid` (8 cores, 16 GB) and `low` whose cores and memory the machine both reaches, memory counting as reached at 90% of the nominal size (a 16 GB machine reports less than 16 GiB); below `mid`, or with memory unknown, it is `low`. Graphics does not set the tier in Phase 1, since no Phase 1 engine uses it. The tier found on the first start is stored as `tier` in `settings.json` in the configuration folder, which the Settings screen changes through `PUT /v1/settings` (M9); later starts keep it. `workers` for a run is the lesser of the active tier's cores (4, 8, 16) and the cores the process may use.

## Packaging

- **Linux:** the Phase 1 package (owner decision B4, 2026-11-09). One installable package containing the interface, the service, the Phase 1 engines and the templates; it installs and runs offline once downloaded (spec 0 principle 6). The format, chosen at M11 (AKS-127, owner to confirm; `docs/research/spec-3-linux-packaging.md`, `docs/DECISIONS.md`): a self-contained archive `ithax-<version>-linux-x86_64.tar.gz`, with `ithax-<version>-linux-x86_64.tar.gz.sha256` beside it, built by `scripts/package_linux.py` into `dist/`. It is unsigned; the README and the archive's `INSTALL.txt` say how to check its checksum (spec 0 "Risks").
  - **Contents.** One folder `ithax-<version>-linux-x86_64/` holding its own Python, `python/` (a relocatable CPython 3.13 from python-build-standalone, its SHA-256 pinned), into which the Phase 1 engines and the other run-time dependencies are installed at the versions and hashes of `packaging/linux/requirements.lock`, and the service from the checkout; the built interface in `python/share/ithax/ui` and the template packages in `python/share/ithax/templates`; the desktop shell, `lib/ithax-desktop`; three commands in `bin/`; `install.sh` and `uninstall.sh`; `LICENSE`, `INSTALL.txt`, `THIRD-PARTY-LICENSES.txt` (every bundled component with its version and licence, checked at build time against `packaging/linux/licences.json`) and `BUILD-INFO.json`.
  - **Install.** Unpack the archive in a folder of the user's choice (the README uses `~/.local/opt`) and run its `install.sh` as the user: no administrator rights, no network. It checks that the bundled Python and the engines import, links the three commands into `~/.local/bin`, writes a desktop entry under `$XDG_DATA_HOME/applications` (default `~/.local/share/applications`), and says whether the desktop shell can run on this machine. `uninstall.sh` removes the links and the entry and leaves the user's projects and settings.
  - **Commands.** `ithax` starts the app: the desktop shell when a display is set and the shell's system libraries (WebKitGTK 4.1, GTK 3, libsoup 3) are all found, with `ITHAX_PYTHON` naming the bundled Python; otherwise the launcher, which opens the interface in the default browser, saying why on standard error. `ithax-launcher` is `python -m ithax.launcher` with its options, for scripts and a machine without a display (`--print-url`); `ithax-mcp` is the MCP server (spec 4). Each unsets `PYTHONHOME` and `PYTHONPATH` and sets `PYTHONNOUSERSITE` and `PYTHONSAFEPATH`, which the service and its run workers inherit, so nothing in the user's own Python folders or the current folder shadows the bundled packages.
  - **Supported.** Linux on x86_64: glibc 2.39 or later for the desktop shell, which is built on Ubuntu 24.04 (where the package is tested), and glibc 2.34 or later for the service and the browser path (the newest wheel tag the dependencies need).
- **Windows:** deferred (owner decision B4, 2026-11-09); the Phase 1 review sets its phase. When built: one installer containing interface, service and Phase 1 engines (proposed default); alternative, an installer plus a prepared WSL image. The code stays platform-neutral meanwhile.
- **Engines:** Phase 1 engines are bundled; an environment manager is introduced with the first Phase 3 engine, so later physics engines can be added without reinstalling the app.

### Service rules

- **Local only.** The service listens on `127.0.0.1` and refuses other addresses unless the user turns on remote access.
- **Token.** `Authorization: Bearer <token>`; the token is 32 random bytes, base64url. WebSocket connections authenticate with a first text message `{"token": "..."}` within 5 seconds, else the server closes with code 1008, because webviews cannot set headers. The token is drawn from the operating system's generator (Python's `secrets`), base64url without padding (43 characters), anew at every start; it is a secret, not simulation randomness, so the spec 1 stream scheme does not apply. Every HTTP request needs it, `GET /v1/system` included; a request without it, or with another, gets 401 with E182 and `WWW-Authenticate: Bearer`. The one exception is the interface's own files: a `GET` (or `HEAD`) of a path under `/v1/ui/` needs no token, since a browser loads the page before the page can send one; the files hold no data, and the `Host` check still applies (AKS-119, owner to confirm). A first message that is not that JSON object with the right token, or none within 5 seconds, closes the WebSocket with 1008 and the reason `E182` (AKS-110).
- **Discovery.** The service binds 127.0.0.1 on a port chosen by the operating system and writes `service.json` `{port, token, pid, started}` with mode 0600 in its configuration folder; the launcher, the MCP server and scripts read it. `port` and `pid` are integers, `token` the token text and `started` ISO 8601 UTC ending in `Z`. The file is written before the service answers (through a temporary file and a rename, so a reader never sees half a file) and removed when the service exits, if it still names this service. The configuration folder is `%APPDATA%\ithax` on Windows, `~/Library/Application Support/ithax` on macOS and `$XDG_CONFIG_HOME/ithax` (default `~/.config/ithax`) elsewhere; the user data folder is `%LOCALAPPDATA%\ithax`, `~/Library/Application Support/ithax` and `$XDG_DATA_HOME/ithax` (default `~/. For one release after the product was named (#70), a folder named `lcsim` in the same place is used while no `ithax` folder exists there, so projects and settings made before the rename are found; the `ithax` folder wins once it exists.local/share/ithax`); `python -m ithax.service --config-dir ... --data-dir ...` overrides both (AKS-110, proposed default, owner to confirm; `lcsim` is renamed with the package).
- **One service per user.** A second start reads the file, probes `GET /v1/system`, and exits if it answers; otherwise it overwrites the file. The probe sends the file's token, goes to `127.0.0.1` without any proxy, and counts as answered only on a 200 within 2 seconds; the second start then exits with status 0 and prints the running service's port (AKS-110). So that two starts at the same moment cannot both serve, a service holds an exclusive lock on `service.lock` in its configuration folder from before it reads the file until it exits; a start that cannot take the lock is the second start, and it keeps probing for up to 10 seconds while the first is still starting, then exits with status 1 if nothing answers (review of PR #34, owner to confirm). The file is also removed when the service is stopped by a signal (`SIGTERM`, `SIGINT`): uvicorn raises the signal again once it has shut down, which ended the process before the file was removed, so the service takes the signal over, removes the file, and then raises it again, so its exit status still says how it was stopped (AKS-119; M7 "Left").
- **Launcher** (AKS-119, owner to confirm). `python -m ithax.launcher` is how the interface finds and starts the service: the desktop shell runs it (Desktop shell below), which on Linux is the default way in since M11 (AKS-142), and scripts, tests and a user without the shell run it directly. It reads `service.json` and probes the service it names, as a second start does; when nothing answers, including when the file is left from a service that has gone, it starts `python -m ithax.service` detached from itself (a new session on Linux and macOS, a new process group without a console on Windows), its output appended to `service.log` in the configuration folder, and waits up to 30 seconds for `service.json` to name a service that answers. It then opens `http://127.0.0.1:<port>/v1/ui/#token=<token>` in the default browser, or with `--print-url` prints that address instead, for scripts and tests; it exits with status 0 then, and with status 1, naming the log, when no service answers in time. `--config-dir`, `--data-dir`, `--ui-dir` and `--idle-minutes` are passed to a service it starts. A browser started with an address holds the token in its command line for a moment, where another user of the same machine could read it; the desktop shell opens its own window instead, and reads the address on a pipe.
- **Desktop shell** (AKS-142, owner to confirm). On Linux the interface's window is the desktop shell, a Tauri 2 program in `desktop/`, built and tested on Linux (the Windows build is deferred with the Windows version, owner decision B4). It opens on its own page ("Starting the engine service…"), then runs the launcher with `--print-url`, with the Python that `ITHAX_PYTHON` names, else `python3` (`python` on Windows) on the search path; the Linux package's `ithax` command sets `ITHAX_PYTHON` to the package's own Python ("Packaging", AKS-127). Of its own arguments it passes on `--config-dir`, `--data-dir`, `--ui-dir` and `--idle-minutes` with their values, and nothing else. It reads the address from the launcher's output on a pipe, so the token is on no command line, and loads it in its window: the interface comes from the service, so the window's origin is the service's own, as in a browser, and the interface makes the same documented `/v1` calls. When the launcher fails, or prints no address of the form `http://127.0.0.1:<port>/v1/ui/#token=<token>`, the shell's page says "The engine service did not start" with the launcher's message, or with the Python that could not be run and `ITHAX_PYTHON`. The webview loads nothing else: a navigation to another origin and a request for a new window are refused (so a link that opens a new window, such as the Results screen's feedback link, does nothing in the shell), no Tauri capability is granted (no command, no plugin), the shell's own page has no script and a content security policy, and the web inspector is off in a release build. Closing the window ends the shell only; the service keeps its own lifetime (Lifetime below).
- **Interface page** (AKS-119, owner to confirm). The page reads the token from the address's fragment, which a browser never sends to the service, removes the fragment from the address bar, and keeps the token in the tab's session storage, so reloading the tab works while the service runs; the next start's token differs, and its address has another port, so another origin, whose storage is empty. Every request the page makes carries `Authorization: Bearer <token>` and `X-Client: ui`, and every WebSocket sends the token message first. The page's preferences are kept in `settings.json` through `PUT /v1/settings`, not in the browser, whose storage changes with the port.
- **Hardening.** Requests whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` are rejected; no CORS headers are sent; WebSocket upgrades carrying an `Origin` other than the interface's own are rejected. Rejection is 403 with E183, checked before the token; for a WebSocket the upgrade is refused before it is accepted, which the server answers with 403. An upgrade without an `Origin` (scripts and the MCP server send none) passes this check (AKS-110, owner to confirm). The interface's own origin is the service's, since the service serves the interface (`GET /v1/ui/{path}`): `http://127.0.0.1:<port>` and `http://localhost:<port>`, the host in any letter case; an upgrade with either passes, and any other `Origin` (another port, `https`, another host, `null`) is refused. The desktop shell adds no origin: it loads the interface from the service, so its window's origin is the service's own (AKS-119, AKS-142, owner to confirm).
- **Lifetime** (proposed default, owner to confirm): the service stays up while runs are active or clients are connected and exits after `idle_timeout_minutes` idle minutes, 30 by default; the interface and the MCP server start it on demand. Idle means no run active, no WebSocket open and no HTTP request in progress; the idle minutes count from the end of the last of these, and at the earliest from when the service starts serving, so the time it takes to start is never idle time (AKS-110, CI on PR #35). The idle time is a setting (owner decision B5, 2026-11-09; built at M11, AKS-141; key, bounds and precedence owner to confirm): `idle_timeout_minutes` in `settings.json` is a whole number from 1 to 10,080 (7 days, the upper bound of `run_time_limit_s`), read as `max_concurrent_runs` is (a JSON integer, not a `bool` or a number with a fraction), default 30; there is no value for "never exit". The service reads it from `settings.json` when it starts (once it holds the service lock, so a second start that finds a running service reads nothing), as it reads the run settings, so a change written with `PUT /v1/settings` (the Settings screen) or in the file takes effect at the next start. A key that is absent takes the default. A value that cannot be used (`null` in the file included) is refused as a W220 issue (spec 1) at `/idle_timeout_minutes`, the default is used, and the service logs it; `GET /v1/settings` lists the issue, after the thresholds' issues. A `settings.json` that exists but cannot be read gives the default too; its W220 issue at `""` is the one "Finding thresholds" gives, so it is listed once. `python -m ithax.service --idle-minutes <minutes>`, when given, sets the idle time of that service, and the setting is not read for it; the launcher passes the option only when it was given one, and the MCP server never does, so a service they start reads the setting unless the launcher was given the option. A run is active from when `POST .../runs` accepts it until it reaches a final state, queued time included (AKS-112).
- **Runs outlive the interface.** Runs are child processes of the service, not of the interface. The service drives each run from a thread of its own and starts its worker as a child process (spec 1 "How the `local` target runs a run"), so a run goes on when the client that started it, or one watching its events, disconnects. Runs do not outlive the service: when the service stops while runs are unfinished, it stops their workers (the cancel grace of spec 1 applies) and marks each `failed` with E191, so no run is left `queued` or `running`; a service that ends without doing so (killed, or the machine stops) leaves that to the next start, which marks them E191 as spec 1 says. The lifetime rule keeps an idle exit from ever stopping a run (AKS-112, owner to confirm).
- **Run queue.** At most `max_concurrent_runs` (default 1, Settings) run at once; others wait in `queued` in arrival order; a run receives `workers` = cores of the active tier. The queue is the service's, across all projects; arrival order is the order in which `POST .../runs` requests were accepted, which are taken one at a time, so a run created first starts first. `workers` is the value `GET /v1/system` reports. The service reads `max_concurrent_runs` (a whole number from 1 to 64), `run_time_limit_s` (a number above 0 and at most 604,800, 7 days; default 600) and `run_memory_limit_bytes` (a whole number from 1 to 2⁶³ − 1, default half the physical memory; spec 4 "Limits") from `settings.json` in the configuration folder when it starts; a key that is absent or holds another value (another kind, a `bool`, or a number out of its range, checked before any conversion so that reading never fails) takes its default, and that is logged (bounds: review of PR #36, owner to confirm). `PUT /v1/settings` writes them (the Settings screen, M9), and they may also be edited in the file; either way a change takes effect at the next start (AKS-112, AKS-119, owner to confirm).
- **Finding thresholds** (AKS-135, owner to confirm). The thresholds of spec 4's finding rules are `finding_thresholds` in `settings.json`, an object with up to five keys: `bottleneck_utilization` and `idle_utilization` (numbers from 0 to 1, defaults 0.85 and 0.30), `relative_half_width` (above 0 and at most 1, default 0.10), `min_time_s` and `min_rate_per_s` (from 0, defaults 60 and 1/3600, the time and rate floors of `not_enough_runs` in seconds and per second). A key that is absent takes its default. The file is read each time `GET .../summary` makes findings, so a change takes effect at the next request without a restart; findings are never stored. A value that is not a number in its range (checked before any conversion, a `bool` refused, as for the run settings), a key that is not one of the five, `finding_thresholds` that is not an object, and a `settings.json` that exists but is not a JSON object the strict reader takes are each refused as a W220 issue (spec 1) at its place in the file, and the default is used for what was refused; the summary and `GET /v1/settings` list these issues in `issues`, and the service logs them. `PUT /v1/settings` writes them (the Settings screen, M9), and they may also be edited in the file (AKS-119).
- **Revision.** Every model write increments an integer `revision`, returned with the model and stored in `project.json`; `PUT .../model` and `POST .../model/edits` accept optional `base_revision`, and a mismatch returns 409 with `{"error": {"code": "E181", ...}, "issues": [], "model": <current>, "revision": N}` and applies nothing. A refused write (400, 409) changes nothing and is not a write. The writes to one project are made one at a time, so two writes stating the same `base_revision` cannot both pass the check. A write first makes both files' final bytes, writes each to a temporary file in the project folder, then renames `model.json` into place and `project.json`, with the new revision, last: that last rename is the commit, and the `model` event is sent only after it. A failure before the commit removes the temporary files, and a failure at it also puts the previous model back, so the revision, the model and the events are unchanged. A service that stops between the two renames leaves the new model under the old revision, which the next write's revision check does not reveal; the rename order was chosen so that the revision never names a model that is not on disk (AKS-111, review of PR #35, owner to confirm).
- **Client header.** Requests may carry `X-Client: ui|mcp|script`, recorded in the run manifest. A request without it counts as `script`; any other value is 400 with E184, checked after the token and before any route runs (AKS-110, owner to confirm).
- **First start.** The interface shows once what the tool does, that results are estimates to support judgement, and where the licence is. That it was shown is remembered as `interface.first_start_seen` in `settings.json`, written with `PUT /v1/settings` when the user presses Continue (AKS-119).
- **Versioned paths.** Every path starts with `/v1`.

- Data (AKS-113, owner to confirm). `POST .../data` takes `multipart/form-data` with the part `file`, the file itself, and optionally the part `units`, a JSON object mapping column names to a Phase 1 time unit (`s`, `min`, `h`, `d`) or `null`; another part, a second file, a `units` that is not such an object, a unit for a column the file does not have or for one whose `type` is not `number` is 400 with E184 at `/file` or `/units/<column>`. The file's name is the part's file name, never taken as a path (the multipart parser, `python-multipart`, keeps only the last part of a Windows path such as `C:\data\a.csv` or `\\server\a.csv`, which old browsers sent): 1 to 100 characters of ASCII letters, digits, space, `.`, `_` and `-`, starting with a letter or a digit and ending in `.csv` or `.xlsx` (any case), whose part before the first `.` is not a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM0` to `COM9`, `LPT0` to `LPT9`, any case); otherwise 400 with E184 at `/file`. A name already in the index is imported again, replacing that file and its entry in place; a name that differs from one in the index only in letter case is 400 with E184, since Windows takes them as one file. The request may be at most 64 MiB plus 64 KiB for the form, checked from `Content-Length` and while it is read; a larger one, or a file of more than 64 MiB, is 400 with E189. A CSV file is UTF-8 (with or without a byte order mark), comma separated with `"` quotes; an `.xlsx` file is read from its first worksheet, formulas by their saved values, from at most 512 MiB unpacked. The first row names the columns: each name is stripped of surrounding spaces and must be non-empty, not a number, at most 200 characters and unlike the others. Every later row is a record; a row whose cells are all empty is skipped, a shorter row has empty cells at its end, and a row with a non-empty cell beyond the header is E189. At most 1,048,576 records and 10,000,000 cells. A cell is a number when it is a finite number (in a CSV, text that follows spec 1's number grammar once stripped), empty when it is empty or only spaces, and text otherwise (an Excel date or a `TRUE` is text). A column's `type` is `number` (at least one number and no text), `text` (at least one text cell) or `empty`. A file that is not UTF-8 text or an Excel workbook (a password-protected workbook is not one), that cannot be read, has no header row or breaks these rules is 400 with E189, and nothing is saved. The response is the file as `GET .../data` lists it, with `preview`: its first 10 records as arrays in column order, each cell a number, text or `null`. The file and its index entry are saved together (each written to a temporary file in `data/`, the file renamed into place, then the index, which commits; a failure at the commit puts the previous file back) while no write of the project's model is under way; validation, a model write and a run's creation read the index and hash the files the same way, so none of them ever meets half an import.
- `GET .../data`: an array of the imported files in the order first imported, each `{name, format, sheet, size, sha256, imported, rows, columns}`: `format` is `csv` or `xlsx`, `sheet` the worksheet read (`null` for a CSV), `size` the file's bytes, `sha256` their hash at import, `imported` ISO 8601 UTC ending in `Z`, `rows` the number of records, and `columns` an array of `{name, type, unit, largest}` in file order, `largest` being a `number` column's largest absolute value as the file holds it (`null` for another type), from which validation tells whether every value is a finite time (spec 1 "Distributions"; review of PR #37).
- `DELETE .../data/{file}`: removes the file's index entry (the commit) and then the file, and returns the remaining files as `GET .../data` lists them; a name not in the index is 404 with E185. A file the model still names may be removed: validation then reports E162 at each reference, and runs already created keep their snapshots.
- `POST .../data/{file}/fit`: the body is `{column}`, text; a name not in the index is 404 with E185, a column the file does not have is 400 with E184 at `/column`, and a column whose `type` is not `number`, or a file now missing or changed since its import, is 400 with E189. The response is `{file, column, unit, values, score, candidates, histogram}`: `values` is the number of values fitted, `score` is `"ks"`, and `candidates` lists, best first (ties in spec 1 order), `{distribution, score}`: `distribution` a spec 1 distribution object, its time fields as quantities in the column's unit (plain numbers when the column has none; a Weibull `shape` is always one), so `set_setting` can take it as it is, and `score` the Kolmogorov–Smirnov statistic of the fit, from 0 (best) to 1. A column whose values are all equal gives `constant` alone; otherwise the candidates are `exponential` (values not negative, mean above zero), `uniform`, `triangular`, `normal`, `lognormal` and `weibull` (values above zero) as far as each fits, by maximum likelihood; `empirical` is not a candidate, since the column itself is written as a `data` reference. A family whose fit fails is left out, and every candidate, `constant` included, passes one gate: it is loaded as the distribution of a time setting by the model layer, and left out if loading reports an error for it (a time field that is not a finite number of seconds, E141; fields that must agree, E160, among them a `uniform` or `triangular` whose fitted `min` is below zero, #69), so every candidate returned is one the model takes as it is (review of PR #37). `histogram` is `{edges, counts}`, the column's values as the file holds them (in the column's unit) counted in bins of equal width, for the Data screen's chart (AKS-120, owner to confirm): with n values, there are k = min(50, ⌈log₂ n⌉ + 1) bins (Sturges' rule) from the smallest value to the largest; `counts` holds k whole numbers that add up to n, a bin holding the values from its lower edge up to but not including its upper edge, the last bin also its upper edge; `edges` holds the k + 1 edges, the first the smallest value and the last the largest; a column whose values are all equal has one bin, both of whose edges are that value. The edges are worked out in units of the largest absolute value, as the fit is, so every edge is a finite number.

The run is made from the bytes of `model.json` as saved, read while no write of the model is under way. In order: loading the file (its errors: 422, `issues` listing every error and warning, `error.code` the first error's code); the target, the request's when given, else the file's (anything but `local` is 422 with E172, at `/target` for the request's); the experiment (none for a `process` model, one for an `optimization` model, or one the model does not have: 400 with E184 at `/experiment_id`); the adapter's `validate` and the fidelity check (422 as for loading). An unknown project is 404 with E185, one that cannot be read 400 with E186. Nothing is created when a check fails. The response is 202 with `{run_id}`, and the run waits in the run queue.

A run that has ended is 409 with E188 (AKS-112, owner to confirm).
- `GET .../summary`: `{summary, findings, issues}`: `summary` as `summary.json` holds it; `findings` the findings of spec 4 "Finding rules" (`ithax.findings.find`), each `{rule, severity, component, scenario, text, evidence}`, in the rules' fixed order, made at the request from the run folder's `summary.json` and `model.json` (the model that ran, never the project's current model, which may have changed since) at the thresholds of "Service rules", Finding thresholds; and `issues` the W220 issues of reading those thresholds, usually empty (AKS-135). ### Model edits

An edit is rejected only when it cannot be applied: unknown or duplicate component id, unknown type, an unknown parameter or experiment named by `remove_parameter`, `remove_experiment`, `set_scenario` or `remove_scenario`, a new parameter without `value` and `type`, a `path` whose parent does not exist. Rejections are issue objects with code E180 and `path` `/edits/<n>`; the batch is then not applied and the response is 400. A batch that applies is saved even if validation then reports errors; the response is 200 with the model, its revision and the issues. `PUT .../model` follows the same principle: the file is saved when it passes the schema pass, and the response carries the meaning-pass issues; a schema failure (E100, E101) returns 400 with those issues and saves nothing. 422 is returned only by `POST .../runs`. The interface and the MCP server both use this one mechanism.

How edits are written and applied (AKS-111, owner to confirm):

- **Shape.** Each edit is an object whose key `edit` names its kind, with the fields of the table and no others. `id`, `new_id`, `type`, `from`, `to` and `experiment_id` are text; `params`, `ui` and `set` are objects; `path` is a JSON Pointer (RFC 6901) as text; `label` is text or `null`; `value`, and the fields of `set_parameter` and `set_experiment` other than `id`, take any JSON value. No field may hold a number JSON cannot hold once read (such as `1e400`), or text that is not valid Unicode. `edits` holds at least one edit. An edit of another shape is 400 with E184, one issue per problem at `/edits/<n>` or `/edits/<n>/<field>`, and nothing is applied: these problems do not depend on the model.
- **Order.** The edits are applied in order, each to the model the earlier ones left. The first edit that cannot be applied is reported, as one E180 issue. An `id` names the first component, experiment or scenario with that id. Since a batch may pass through states the schema pass would refuse, an edit meets the model in any shape: a list or object it must change is created when absent and cannot be applied when it is of another kind (E180), what it only reads is skipped where it cannot be read, and an edit is always applied or rejected with E180, never answered with 500 (review of PR #35).
- **Pointers.** In a `path`, an array is addressed by an index without leading zeros; `set_setting` and `set_path` replace the entry at an index, and append at `-` or at the array's length. A `path` of `""` names no setting or key and cannot be applied. `set_path` and `remove_path` reach `/meta`, `/run`, `/objectives`, `/constraints` and `/experiments/<n>/search`, and in an `optimization` model `/variables`, `/objective`, `/sets` and `/tables` (the last two since AKS-123), and what lies below them; another `path` cannot be applied. `remove_path` cannot be applied to a `path` that does not exist.
- **Schema.** A batch whose result would not pass the schema pass cannot be applied, so `model.json` always passes it: E180 is reported at the edit after the last one that left the model passing, and its message gives the first schema issue. Examples: `set_path` of `/meta/name` to a number, `remove_path` of `/meta`, `connect` or `set_experiment` in an `optimization` model.
- **Names.** `set_scenario` cannot be applied when its `set` names a parameter the model does not have, and `remove_scenario` when the experiment has no scenario of that `id`. `connect` and `disconnect` name ports, not component ids: a `connect` to an unknown component or port is applied and the meaning pass reports it (E130), and a `disconnect` of a port with no connection changes nothing. A `connect` leaves exactly one connection from its `from`. `remove_component` removes every connection whose `from` or `to` names the component; settings and metrics that still name it are reported by the meaning pass (E124, E174). `rename_component` rewrites the component part of connection ends, every setting its type declares as naming a component (`pool`, `target`) that names it, and every objective and constraint `metric` that starts with `<id>.`; a `new_id` that another component has cannot be applied. `remove_parameter` treats as references a `{"$param": id}` in any component setting, a scenario `set` key and a `search.variables` entry. `set_parameter` and `set_experiment` set fields and never remove one.
- **Domain.** No edit changes `domain`. A project's domain is chosen when it is created (`domain` on `POST /v1/projects`) and changes only by writing a whole model with `PUT .../model`, which closes the gap the owner design review left for M6.

### Status codes and errors

| Code | When |
| --- | --- |
| 200 | Success |
| 202 | Run accepted |
| 400 | Request malformed (E184); an edit that cannot be applied (E180); a model file that fails the schema pass (E100, E101); a project folder that cannot be used (E186); a data file that cannot be imported or a column that cannot be fitted (E189) |
| 401 | Token missing or wrong |
| 404 | Project, run, table, data file or interface file not found |
| 409 | Action not allowed in the run's current state (E188), or the model revision has changed (E181) |
| 422 | `POST .../runs` only: the model has validation errors; the body lists the issues |
| 403 | Refused by the hardening rules: `Host` or WebSocket `Origin` not allowed (E183) |
| 405 | Method not allowed on a documented path (E185) |
| 500 | The service failed; the details are in its log, never in the body (E187) |

Every error body is `{"error": {"code", "message"}, "issues": [...]}`, where issues use the spec 1 issue object. `error.code` is a spec 1 code (AKS-110, owner to confirm): E182 for 401, E183 for 403, E184 for a malformed request (body not JSON, a field missing, unknown or of the wrong kind, a bad `X-Client`), E185 for an unknown project, template, component type or path (404) or method (405), E186 for a project folder that cannot be used (400), E187 for 500, and the codes the rows above name: E180 at `/edits/<n>` and the E100 or E101 issues of a `PUT` are listed in `issues`, and a 409 with E181 has none (AKS-111, owner to confirm); E188 for a 409 of the run endpoints, and for a 422 the first error's code (E172 for a target), its issues listed (AKS-112, owner to confirm); E189 for a data file or column that cannot be used, its `issues` one issue whose `path` is `/file` or `/column` (AKS-113, owner to confirm). For E184 `issues` holds one issue per problem, its `path` a JSON Pointer into the request body as E180's `/edits/<n>` is; otherwise `issues` is empty unless the row says it lists them.

### Progress events

```json
{"type": "progress", "fraction": 0.4, "message": "Scenario 1 of 2, replication 12 of 30"}
{"type": "metrics", "scenario": "default", "values": {"till.wait.mean": 268.1}}
{"type": "state", "state": "done"}
```

On connection the stream first sends `{"type": "state", ...}` and the latest `progress` event, then live events; after a terminal state the server sends it and closes. A client may connect at any time, including after `done`.

How the stream is built (AKS-112, owner to confirm): after the token message (as for every WebSocket), a run that cannot be found closes the connection with 1008 and the reason `E185`. The first two events are the run's state and progress at one instant, so no change is missed or sent twice: an event that changed them before that instant is not sent, and every later one is. `progress` is `{"type": "progress", "fraction", "message"}` with the manifest's `fraction` and `message` as "A run as the run endpoints show it" defines it; live `progress` events follow every report of the adapter (for a search, the weighted fraction and the "Search, candidate n" or "Confirmation, candidate n" message of spec 2). After the final state the server closes with 1000; a run already final sends its state and progress and closes. A final state is made visible (the run endpoints, this stream, the project's `run` events) only once the run has finished on disk and freed its queue place (spec 1 "Finishing order"); until then the run endpoints show the run as last published, so a stream opened while the manifest is already final starts from `running` and then sends the final state, once (CI on PR #36, owner to confirm). `metrics` events are sent only for an adapter that reports live metrics, and no Phase 1 adapter does, so none is sent yet. What the client sends after the token is ignored.

### Project folder

```text
<project>/
  project.json    id, name, created, layout_version, model_revision
  model.json      the current model
  data/           imported files, unchanged, plus a column index
  runs/           one folder per run, as in spec 1
  index.sqlite    run index, rebuilt from runs/ if missing
```

`index.sqlite` is a cache: the run ids of `runs/` in the order the runs were accepted, with `created` and `experiment_id`. The manifests are the source of truth, so a run's state is always read from its `manifest.json`. When the service first uses a project's runs (on start for every registered project), it rebuilds the index if it is missing or cannot be read (in the order of `created`, then `run_id`), adds the run folders it lacks and drops those that are gone (AKS-112, owner to confirm).

`project.json` holds `{id, name, created, layout_version, model_revision}`; `id` is a UUID4 string and is `pid`. The model's own `format_version` is inside `model.json`. `created` is ISO 8601 UTC ending in `Z`; `layout_version` is 1 for the layout above; `model_revision` is 0 for a new project (AKS-110). Every number the service reads from disk and then uses has a declared kind and range (review of PR #36, owner to confirm): `layout_version` is a whole number from 1 and `model_revision` one from 0, each at most 2⁶³ − 1; a `bool`, a float, text or a value out of range makes `project.json` unreadable (E186). A write that would take the revision past 2⁶³ − 1 is 400 with E186 and saves nothing.

`data/` holds each imported file under its name, unchanged, and the column index `data/index.json`: `{"index_version": 1, "files": [...]}`, each file as `GET .../data` lists it. The index is read by the strict reader, with every number of a declared kind and range (`size` and `rows` whole numbers from 0 to 2⁶³ − 1, `sha256` 64 lower-case hexadecimal digits, `type` one of the three words, `unit` a Phase 1 time unit or `null`, `largest` a finite number from 0 for a `number` column and `null` otherwise); an index that cannot be read, or holds a name the naming rule refuses, is taken as empty, so every `data` reference is E162 until the files are imported again, which writes a new index (AKS-113, owner to confirm).

The folder is plain files so it can be copied, zipped or put under version control. The project folder, not the model file alone, is the unit to share when a model uses imported data; the Results screen's export produces a zip of the project folder through `GET /v1/projects/{pid}/export` (AKS-138), which leaves out `index.sqlite` and the runs that have not ended.

### Canvas behaviour

These are functional rules. Visual design is covered by the checklist below.

- **Single source.** The canvas shows the model file and nothing else. Every canvas action is one or more model edits.
- **Add.** Dragging a block from the palette adds a component with a generated id, such as `server_2`, and default settings. How (AKS-136, owner to confirm): the id is `<type>_<n>`, `n` one more than the highest number any component id of that form holds (so a deleted block's id is not given to the next, and a renamed block's is not taken); the edit is `add_component` with `params` `{}` and `ui` `{"x", "y"}` at the drop point. A setting the type gives a default is left out, since an absent setting takes its default (spec 1), and a required setting with no default is left out too, so validation reports it (E122) until the user fills it in; a block therefore writes only what the model needs.
- **Connect.** Dragging from an output port to an input port sends `connect`. Dragging from an output port that is already connected replaces its connection.
- **Delete.** Removes the selection and its connections, after a confirmation the user can turn off in Settings (on by default).
- **Undo and redo.** At least 100 steps, covering every model edit. Each step stores the model as it was; undo and redo write the stored model with `PUT .../model` and `base_revision`, because some edits (such as `set_setting` creating a new key) have no inverse edit. The number of steps is Settings' `undo_steps`, or the tier's recommendation when it is `null` (AKS-136).
- **Clearing.** No edit removes a component setting or a parameter's `min` or `max`, so clearing an optional one writes the whole model without it, with `PUT .../model` and `base_revision`, as undo does; it is one undo step (AKS-136, owner to confirm).
- **Save.** Automatic after every edit. There is no save button. One write at a time: while a write (or a reload of the model) awaits its answer, the canvas takes no other change, so every action is computed from the model shown, which holds every accepted write; its model-changing controls are unavailable but keep the focus, a text field's commit is refused, the field shows the saved value again and a notice says the change was not saved because the canvas was saving and to make it again (nothing is kept or sent later), and the save state shows "Saving…" (AKS-136, review of PR #45, owner to confirm). While a write gets no answer from the service, the canvas is read-only and the same write is retried every 2 seconds (owner design review, choice 8; AKS-136).
- **Validate.** Runs half a second after the last edit. Issues appear as a marker on the block and in a list; selecting a list entry selects the block.
- **Run.** Disabled while errors exist, or while a write or validation is pending, with the reason shown (owner design review, choice 9; AKS-136).
- **Rename.** Changing a component's id updates its connections and any references to its metrics. The side panel's Id field sends `rename_component`; a block's label is set with `set_label` (AKS-136).
- **External edits.** The canvas sends `base_revision` on every write and, on a `model` event whose revision it did not produce, reloads the model and shows a one-line notice naming the client. The reload clears the undo and redo history, so an undo cannot silently revert another client's change. The canvas marks what the other client added, changed or removed, and the user can accept or reject each change; a rejection is an ordinary write of the model with that item restored, sent with `PUT .../model` and `base_revision`. How (AKS-137, review of PR #46, owner to confirm): a 409 with E181 is an outside change too, and its notice says the canvas's last change was not saved. The notice names each client whose `model` event lies between the revision shown and the one read ("by an assistant (mcp)", "by a script (script)", "in another window (ui)", "by another program" when none is known), and stays until dismissed or replaced. The canvas keeps one baseline: the model shown before the first outside change not yet reviewed, with the user's own writes since taken into it, so they are never marked. The marks are always the comparison of the baseline with the model shown, item by item by stable id: components by `id`, connections by `from`, parameters by name, experiments, `objectives`, variables and constraints by `id`, an `optimization` model's `objective` as one item, and every other top-level key (`meta`, `run`, ...) as one item; a list that is not a list of objects with distinct ids is one item; key order and list order are not changes; a rename is a removal and an addition. A later outside change is compared with the same baseline, so changes compose without being tracked one by one, and an item the other client puts back is no longer marked. Accept takes that item as shown into the baseline and writes nothing; Accept all makes the model shown the baseline. Reject writes the model shown with that item as in the baseline (a removed one put back at its place in its list), one undo step; Reject all writes the baseline, one undo step. Accept and Reject follow the Save rule: while a write awaits its answer they are unavailable. Names a model holds (parameter, decision and coefficient names, types, ports) are looked up as own properties only, so `constructor` or `__proto__` is an ordinary name.
- **Optimization models.** The Canvas screen of an `optimization` model has a Table view and a Diagram view of the same model, with a switch; the Table view is shown first. In the Table view the variables are "Decisions" (name, kind, lower and upper bound), the objective is the "Goal" (maximize or minimize, and one coefficient per decision) and the constraints are "Limits" (name, one coefficient per decision, at most, at least or exactly, and the limit). Every change is one batch of `set_path` and `remove_path` edits on `/variables`, `/objective` and `/constraints`, one undo step, under the Save rule. Emptying an optional field (a bound, a coefficient) removes it with `remove_path`; a number is sent as a number when it follows spec 1's number grammar and as typed otherwise. Renaming a decision also renames its coefficients in the goal and the limits, in the same batch, unless another decision has the new name (the service then reports the duplicate); removing one removes its coefficients with it. A new decision is `{"id": "decision_<n>", "type": "continuous"}` and a new limit `{"id": "limit_<n>", "linear": {}, "op": "<=", "rhs": 0}` (the schema needs `op` and `rhs`), `n` as in Add. A field shows the issues whose `path` names it. The Diagram view draws each decision as a card on the left and the goal and each limit as a card on the right, with a line from a decision to each card whose coefficients name it, labelled with the coefficient; the layout is computed and nothing about it is stored, and choosing a card opens its row in the Table view. The screen has no experiment picker. Spec 1's variables hold no unit or icon, so a decision's name is its id (AKS-137, owner to confirm). An indexed model (spec 1 "Indexed optimization", format 0.2) opens in both views as written, not expanded (AKS-123, owner to confirm): a notice says the plan is indexed and that its sets, tables and terms are changed in the model file or by an assistant, not in these views; a decision with `over` says what it repeats over ("one for each depots × customers") and has no coefficient field, since its coefficients are its terms; the goal and each limit are read in words with their terms ("For each depots: Σ over customers ship[depots, customers] ≤ supply[depots]"), the limits in a "Reads as" column; a `{"$table": ...}` limit is shown as text, not as a field; and the Diagram view draws one line from a decision to each card it adds to, labelled with every part it adds there, joined with "+": a coefficient, a coefficient keyed by an expanded name with its members (`1 [north,park]`) and each term's table id or number (`150 + 50`, `cost + 2`; review of PR #53). Renaming, removing and the Diagram read one resolver (`references` in `ui/src/canvas/plan.ts`) that maps each coefficient key (an id or `id[...]`) and each term to its declared decision. Renaming a decision also renames the terms that name it and the coefficients keyed by its expanded names (`ship[north,park]` in a `linear`), and removing one removes them, in the same batch (review of PR #53). The Run monitor and Results show the expanded names the service reports (`ship[north,city]`).
- **Try a change.** Beside a number or time field of the side panel (also one inside a distribution, not a whole distribution) "Try a change" asks the value to try and a name for the option, and sends one batch of edits, one undo step, under the Save rule, built from the model shown (`docs/design/canvas-interactions.md` "Trying a change"): `set_parameter` creating a parameter named `<block>_<field path joined by _>` (with `_2`, `_3` when taken; every id it makes is cut to spec 1's 64 characters with room for the suffix, so it is always a valid identifier) holding the field's value, of type `quantity` for a time, `integer` for a whole-number setting and `number` otherwise; `set_setting` linking the field to it at the field itself; `set_scenario` adding `baseline` (or `baseline_2`, ...) with an empty `set` when the experiment chosen in the top bar has no scenarios of its own; and `set_scenario` adding the option, its id the name typed made an identifier (lower case, other characters as `_`, `option_` before one that does not start with a letter, at most 64 characters), never one already taken or `default`, its `set` giving the parameter the value tried (as typed for a `quantity`, a number by spec 1's number grammar otherwise). A field already linked to a parameter adds only the scenarios. The form closes whenever the model shown changes; with no experiment it says so and sends nothing (AKS-120, owner to confirm).
- **Data and Experiment screens.** These screens change the model through the same session as the canvas, so the Save and External edits rules hold on them too: one write at a time, every control that changes the model unavailable while a write or reload awaits its answer, a draft (a typed id, a "Use for" choice, the waiting question's answer) never outliving a change to the model shown, an outside change reloading the model with its notice and the list of changes to review, and Undo and Redo in the top bar. The Experiment screen sets an experiment's fields with `set_experiment`, clearing an optional one by writing the whole model without it (no edit removes a field); its scenarios with `set_scenario` (one column per parameter, an empty cell leaving the parameter out of `set`) and `remove_scenario`; `objectives` and `constraints` with `set_path` and `remove_path`, renaming an objective also renaming the `search.objective` that names it in the same batch unless another objective has the new name; and an experiment's `search` with `set_path` and `remove_path` on `/experiments/<n>/search` (turning it on writes `{"objective": <the first objective's id, or "">}`). An `optimization` model has no experiments, which the screen says. The Data screen uses the four data routes, and writes a block's distribution setting with `set_setting`: the candidate chosen as the fit returned it, or `{"dist": "empirical", "data": {"file", "column"}}`; before a server's `service` or a delay's `time` it asks "Does this column include time spent waiting?", setting it on No and, after a warning, on "Use it anyway" for Yes or Not sure. A number column's unit is chosen by importing the file again with `units`, which needs the file picked in that window; a fit belongs to the listing of files it was computed from, so any import or removal (a unit change keeps the bytes and their hash) drops it until the column is fitted again; the preview of 10 records is the import's answer, so it is shown for files imported in that window. After an import or a removal the model is validated again, since `data` references read the column index (AKS-120, owner to confirm).
- **References.** Blocks without ports (`resource_pool`, `schedule`, `failure`) are placed like any block. Their `pool` and `target` settings are drawn as reference lines, which are not connections and differ by kind in pattern, icon and word; they are set in the side panel with `set_setting`.

### Run monitor, Results and Settings

How the last three screens work (AKS-138, owner to confirm). The rules of "Canvas behaviour", Save, hold for every request that changes something: one at a time per screen, the controls that would send another inert while it awaits its answer, a refused one shown as the service's issue objects; every action is computed from what is shown; nothing is queued, kept for later or held only in the interface.

- **Starting a run.** The Canvas's Run sends `POST .../runs` with the experiment chosen in the top bar for a `process` model and no `experiment_id` for an `optimization` model, under the Canvas's Run rule. While the request awaits its answer, Run is unavailable. A `202` opens the Run monitor at the new run (`#/monitor/<pid>/<run id>`); a refusal (the 422 of a model with errors, E172, a 400) shows the service's issues on the Canvas and starts nothing.
- **Run monitor.** It shows the run its address names, or else the project's most recently accepted run that is `queued` or `running`, or else its most recent run, so a page opened or reloaded while a run goes on finds that run. It shows the run's state, progress fraction and the service's message from `GET /v1/runs/{rid}/events`, which starts with the state and the latest progress ("Progress events"); a stream that closes before a final state says contact was lost and offers to connect again. Live key numbers are not shown: no Phase 1 adapter sends `metrics` events, and the screen says so; with nothing else updating, it has no "Pause updates". Cancel sends `POST /v1/runs/{rid}/cancel` for the run shown (a 409 with E188 is shown as the service's issue); what the run does next is read from its events. The project's runs are listed from `GET .../runs`, read when the screen opens and again at each `run` event of `GET /v1/projects/{pid}/events`, each with Watch, Cancel while it is `queued` or `running`, and Results once it is `done`. A search run shows the service's "Search, candidate n" and "Confirmation, candidate n" messages; its best-so-far chart is on Results.
- **Results.** It shows the run its address names, or else the project's most recent `done` run, from `GET /v1/runs/{rid}`, `GET .../summary` and, for a `process` run, `GET .../tables/replications` and `GET .../tables/timeseries` (JSON); everything shown is derived from these answers for that run id, and nothing is kept when the run shown changes. A run that is not `done` is said to be so, with a way to the Run monitor. The order is: a headline card, the run's first finding in the rules' order (spec 4), or, with none, that no finding rule fired at the thresholds in Settings; the findings, each with its rule in plain words, and the summary's `issues` (W220) as the service wrote them; the key numbers of each scenario, every metric of `summary.json` in its order with its average, its likely range (± the half-width) and its repeat runs (`n`), in display units chosen by the interface by the display rules of spec 4 "Finding rules" (times in the largest Phase 1 unit they reach, rates per hour, fractions as percentages, three significant figures, an undefined value as "not defined"), while `summary.json` and the tables stay in SI units; the differences between scenarios, when there are any; then the charts of the run's kind, each with a data table ("Show as table"); then the replications table. For a `process` run the charts are bars of every server's (and pool's) utilization and of every wait, one bar per component and scenario on one category axis with its likely range at that bar, both bounds within the axis, and the average of the repeat runs over time of one `timeseries` metric at a time, one line per scenario. For a search run (`summary.json` holds `search`) they are the trials in the order evaluated, each the objective metric's average, filled when it meets every limit and hollow when it does not, with a line at the best found (`search.objective.after`), and the table of all trials (the values set, the objective metric's average and likely range, whether it meets every limit, whether it was checked with the full repeat runs, the best marked); a best-so-far step line needs the objective's sense, which `summary.json` does not hold, so it is not drawn. For an `optimization` run they are the decisions' values, the goal's value and status, and the limits with those that are fully used (`tight`) named. The footer, on the page and on every page of the PDF, names the model (`summary.json`'s `model`), the run id, `fidelity_label`, the replications and confidence (`replications` and `confidence`; "not replicated" for an `optimization` run, which has neither), the engine's name and version (the run's `engine`) and "Simulation results are estimates and carry no warranty." Exports: each table as CSV from `?format=csv`; a PDF made in the page with the headline, findings, key numbers and the run kind's tables, its footer on every page; and the project zip from `GET .../export`. "Tell us what you built" is a link to the project's issue page that opens the browser and fetches nothing (spec 0 "Success measures").
- **Settings.** It reads `GET /v1/settings`, `GET /v1/system` and `GET /v1/engines` when it opens, and writes every change with one `PUT /v1/settings`: a typed value is sent as a number when it follows spec 1's number grammar and as typed otherwise, so the service checks it, an emptied field sends `null` (its default), and `finding_thresholds` and `interface` are sent whole, the shown values with the one change; an emptied threshold is left out of the object, which restores its default, since `null` is not a threshold value (review of PR #48). A refused write shows the service's E184 issues and every field shows the saved value again. ### Performance targets

All proposed, to be measured on the low tier (proposed; measured per the Build guide protocol, confirmed by the owner):

- Service ready within 5 seconds of start.
- Canvas stays responsive with 200 components: an end-to-end test adds 200 components by API and selecting a block paints within 100 ms (proposed).
- Validation of a 200-component model within 200 milliseconds.
- Service uses under 300 MB of memory when idle.

How the three service targets are measured (AKS-114, owner to confirm; `tests/perf/test_service.py`): "ready" is the first 200 from `GET /v1/system`, timed from just before `python -m ithax.service` is started; validation is `POST .../validate` of a model of 200 components (a source, 198 servers in a line and a sink) timed from request to response over loopback HTTP, the largest of 20 calls; idle memory is the resident memory of the service and every process it started, after 5 seconds with no request, both just after the start and after a run has ended, with 300 MB read as 300,000,000 bytes. Measured at M6 on 4 cores (`docs/research/perf-M6.md`; not the low tier, owner to confirm): on Python 3.13, ready in at most 1.4 seconds, validation in at most 0.16 seconds (median 0.08), idle at 178 MiB after the start and 249 MiB (261 MB) after a run; on Python 3.11 within 5% of these, idle at 257 MiB (269 MB) after a run.

How the canvas target is measured (AKS-121, owner to confirm; `tests/perf/test_interface.py`, which starts the service with the built interface and runs `ui/perf/canvas.perf.ts` in Chromium): a model of 200 components (a source, 198 servers in a line and a sink, placed in a grid of 20 columns) is written with `PUT .../model`, the Canvas opens on it at 1,280 × 800, fitted to the view, and 12 drawn blocks are clicked in turn; one selection is timed from the click's `pointerdown` to the first frame painted after the block is drawn selected and the side panel names it, and the largest of the 12 is the measurement. Measured at M9 on 4 cores, Python 3.13 and Chromium 153 (`docs/research/perf-M9.md`; not the low tier, owner to confirm): at most 30 to 36 ms in four runs, median 20 to 22 ms, against 100 ms; the Canvas opened in about 2 s; with the interface served the service was ready in at most 1.4 s and idled at 183 MiB (192 MB) after the page had loaded the canvas; the interface's JavaScript is 1,283 kB (396 kB gzipped) and its CSS 54 kB.
