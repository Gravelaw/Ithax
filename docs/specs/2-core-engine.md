# Spec 2: Core Engine for Process Simulation and Optimization

> Version 1.0 · working copy in the repository (source of truth, owner to confirm) · changes are listed under "Changes in this version".

Two engine adapters, both in Python: discrete-event simulation on SimPy, and optimization on HiGHS; Optuna is a search driver inside the experiment manager, not an adapter. Together with an experiment manager they make Phase 1 a complete product.

> **Warning: partly tested.** Five block types ran in a prototype and, from M2, in the SimPy adapter and its benchmarks; from M4 the other seven (`queue`, `batch`, `unbatch`, `store`, `resource_pool`, `schedule` and `failure`) run there too, each with a unit test and a benchmark. The optimization layout in the model file runs from M5 in the HiGHS adapter (AKS-108), with the four optimization benchmarks, and its indexed form (sets and tables) from M10 (AKS-123), with the transport benchmark, and simulation-based optimization runs from M5 in the experiment manager (AKS-109), with the machine-count benchmark. Performance targets are proposals. Verify each at its milestone and update this spec. See "Known gaps" in the Build guide.

## Scope

- **In:** the process block library, probability distributions, the experiment manager, mathematical optimization, simulation-based optimization, benchmarks.
- **Out:** agent-based and system dynamics models (spec 5), any physics (spec 6).

## Process block library

| Block | Models |
| --- | --- |
| Source | Arrivals, by distribution or from a schedule |
| Queue | A waiting line with a discipline (first in first out, last in first out) and optional capacity |
| Server | A resource that processes items, with capacity and service time |
| Delay | A fixed or random wait with no resource, such as transport or drying |
| Branch | Routing by probability or shortest queue |
| Batch, Unbatch | Grouping items and splitting them again |
| Store | Inventory with a reorder rule |
| Resource pool | Shared staff or tools needed by several servers |
| Schedule | Shifts and breaks applied to a server or pool |
| Failure | Random breakdown and repair of a server |
| Sink | Departure, where statistics are recorded |

Distributions: exponential, normal, lognormal, triangular, uniform, Weibull, constant, and empirical from imported data.

## Outputs

Throughput, cycle time, waiting time and queue length per queue, utilization per server and pool, work in progress, stock level and stock-outs per store. Each comes as a mean, a confidence interval and a time series.

## Experiment manager

- **Replications:** every replication draws its random streams from the experiment seed as spec 1 defines; the seed is recorded in the manifest.
- **Warm-up:** an initial period is excluded from statistics.
- **Confidence intervals:** 95% by default, computed across replications.
- **Scenarios:** named sets of parameter values, compared as paired differences with their own confidence intervals.
- **Parallel runs:** replications use all available processor cores.

## Optimization

| Kind | Use | Engine |
| --- | --- | --- |
| Mathematical | Problems written as an objective and constraints: product mix, transport, assignment, blending, scheduling | HiGHS through Pyomo |
| Simulation-based | Finding the best parameter values of a simulation model, such as number of machines | Optuna, with a set replication budget per candidate |

Mathematical problems are entered in a table-style editor: decision variables, objective, constraints. Simulation-based optimization picks any entries from `parameters` as variables and any output as the objective.

## Benchmarks

| Case | Known answer | Milestone |
| --- | --- | --- |
| Single server queue with random arrivals and service (M/M/1) | Mean wait from queueing theory | M2 |
| Multi-server queue (M/M/c) | Erlang C formula | M2 |
| Two queues in series | Product-form result | M2 |
| Delay | Little's law | M2 |
| Branch by probability | Weighted split of arrivals | M2 |
| Queue with loss | M/M/1/K loss formula | M4 |
| Batch and unbatch | Mean batch wait (size − 1)/(2λ) | M4 |
| Store, deterministic | Cycle analysis | M4 |
| Resource pool | M/M/1 and M/M/2 through a pool | M4 |
| Schedule, deterministic | Event-by-event calculation | M4 |
| Failure | Availability MTTF/(MTTF + MTTR) | M4 |
| Four small linear and integer programs | Answers verified by enumeration, listed below | M5 |
| Transport plan | Optimum by LP duality: a feasible plan and dual prices of equal cost | M10 |
| Machine count, simulation-based | Erlang C | M5 |

A simulation benchmark checks every known answer in its row. A check passes when |estimate − known answer| ≤ 3 × standard error, the standard error being the sample standard deviation of the replication means divided by √n (a correct engine fails about 3 in 1,000 rerolls rather than 1 in 20). Deterministic cases must match exactly to four significant figures. Optimization benchmarks pass when the objective matches to four significant figures. Benchmark seeds are fixed in the benchmark files and queue cases use 100 replications so that a 5% bias in a mean wait is detected. A failure after a change that alters random-number use is investigated and recorded in `docs/DECISIONS.md`; a seed is changed only when the coverage run (20 consecutive seeds, `pytest -m benchmark_coverage`, run by hand) shows the case passing at least 19 of 20 times, proving a reroll, and the entry cites that run.

## Detailed specification

The sections below are binding. Where they differ from the summary above, these win.

### Block reference

| Type | Ports | Settings | Behaviour |
| --- | --- | --- | --- |
| `source` | `out` | `interarrival` (distribution), optional `first_arrival` (time quantity), `max_items` (integer) | Creates one item, waits one interarrival time, repeats. The first item is created at `first_arrival`, 0 s when absent; after `max_items` items the source stops (proposed default, owner to confirm) |
| `server` | `in`, `out` | `capacity` (integer), `service` (distribution), optional `queue_capacity` (integer), `discipline`, `pool` | Items wait in the server's own queue, then hold one unit of capacity for one service time |
| `delay` | `in`, `out` | `time` (distribution) | Holds each item for the sampled time; no queue, no capacity limit |
| `branch` | `in`, one output per route | `routes` (array of identifiers, required; one output port per entry, named by the entry), `rule` (`probability` or `shortest_queue`), `weights` (object keyed by route, required for `probability`) | Sends each item down one route |
| `queue` | `in`, `out` | `capacity` (integer), optional `discipline`, optional `on_full` (`block`, default, or `discard`: the item leaves and is counted in `<queue>.discarded`) | A standalone buffer, for use ahead of a batch or branch |
| `batch` | `in`, `out` | `size` (integer), optional `timeout` (time quantity) | Collects `size` items and releases them as one |
| `unbatch` | `in`, `out` | none | Splits a batch back into its items |
| `store` | `in`, `out` | `initial`, `reorder_point`, `order_quantity` (integers), `lead_time` (distribution) | Each item arriving at `in` takes one unit of stock and leaves by `out` at once. If stock is zero the item waits, first in first out, until a delivery; each such item counts as a stock-out. When stock on hand plus on order falls to `reorder_point`, an order of `order_quantity` is placed and arrives after `lead_time` (a distribution) |
| `resource_pool` | none | `capacity` (integer) | Shared staff or tools; servers name it in their `pool` setting |
| `schedule` | none | `target`, `shifts`, optional `period` (time quantity, default 24 h) | Changes the capacity of a server or pool over time |
| `failure` | none | `target`, `time_to_failure`, `time_to_repair` | Takes a server out of service at random and returns it after repair |
| `sink` | `in` | none | Removes the item and records its statistics |

Item attributes, the `attribute` rule and priority disciplines are deferred to Phase 2 (see spec 1).

Rules that apply across blocks:

- **Server queue.** Unlimited and first in, first out unless `queue_capacity` or `discipline` says otherwise.
- **Discipline.** `discipline` values are `fifo` (default) or `lifo`.
- **Blocking.** If the next block cannot accept an item, the item stays where it is and keeps holding its capacity. In M2 only a server with `queue_capacity` can refuse: it accepts an item while a unit is free or fewer than `queue_capacity` items wait (so `queue_capacity` 0 accepts only into a free unit). A server whose finished item is refused keeps it on its unit, which stays busy (and counts as busy in `utilization`) until the item moves; a delay always accepts and holds a refused item past its sampled time; a branch always accepts and keeps a refused item itself, so the unit upstream of a branch is freed. A blocked item moves as soon as space frees at the block that refused it, at that same instant and before any other event due then, blocked items going in the order they were refused (first in, first out). A source never blocks (see "Source when blocked"); since a branch always accepts, a source feeding a branch never discards. Proposed default (AKS-99), owner to confirm. From M4 (AKS-105, owner to confirm) a full `queue` with `on_full` `block` also refuses, so a server feeding it stays blocked and a source feeding it discards; a `queue` with `discard`, a `batch` and an `unbatch` always accept, so a source feeding one of them never discards. A `store` always accepts too (AKS-106, owner to confirm): an item that finds no stock waits at the store, and an item that has taken its unit but is refused by the next block keeps the unit and waits at the store, in the order refused, until space frees there.
- **Branch rules.** `probability` draws from the branch's own stream and picks a route with probability weight/sum of weights. `shortest_queue` picks the route whose next block has the fewest waiting items (0 for a block without a queue); ties go to the earliest route in `routes`. The route is chosen when the item reaches the branch. `probability` draws one number per item, even when only one weight is above 0: a uniform u in [0, 1), and the first route whose running sum of weights, in `routes` order, exceeds u × sum of weights; a route of weight 0 is never chosen. `shortest_queue` draws nothing and ignores `weights`. A server's waiting items are its queue, not the items on its units; a delay, a branch and a sink count 0. Proposed default (AKS-99), owner to confirm. A `queue`'s waiting items are every item it holds; a `batch` and an `unbatch` count 0, having no queue (AKS-105, owner to confirm). A `store`'s waiting items are the items waiting for stock, not those that have their unit and are refused by the next block (AKS-106, owner to confirm). A server with `pool` counts, besides its queue, the items holding one of its units while they wait for a pool unit (AKS-107, owner to confirm).
- **Simultaneous events.** Events at the same time run in the order they were scheduled, with SimPy's one exception: the first step of a process started at that instant, and an interrupt, run before the other events due then (SimPy orders events by time, then urgent before normal priority, then scheduling order). An event due exactly at the end of the run does not run.
- **Queue.** A `queue` passes an item to `out` as soon as the next block accepts it, so an item that passes straight through waits 0 s and is never counted as waiting, even for no time; the others wait, and `discipline` picks the one that moves when space frees at the next block (`lifo`: the latest to arrive at that moment). An item held by the queue counts against `capacity` until it moves. Items arriving together (the items of one batch from an `unbatch`) can find the queue full only because its offer of an earlier item to the next block is still due at that instant. A blocking queue then refuses them, and they move in at that same instant as the offer frees space, in the order they were refused ("Blocking"). A discarding queue holds them until that offer has been tried: each then enters while there is room, and is discarded only if the queue is still full with its offer refused. So items arriving together are neither discarded nor delayed while they can move on. With `on_full` `discard`, an item arriving at a full queue whose offer has been refused leaves the model at once: it is counted in `<queue>.discarded` and leaves work in progress, and it has no wait. Proposed default (AKS-105), owner to confirm.
- **Batch and unbatch.** A batch is one unit holding the units it collected, in arrival order; it moves through blocks as one unit (one place in a `capacity`, one service). Its creation time is the creation time of the first unit to arrive at the batch. The `timeout` of "Batch timeout" is started per batch when its first unit arrives, and a batch filled before its timeout is not released again by it. When the next block refuses a formed batch, the batch waits at the `batch` block for space there, while the next batch collects; a `batch` holds any number of formed batches and always accepts. An `unbatch` sends on, at once and in order, the units of what it receives, one level of batching (a batch of batches gives batches), and passes a single item on unchanged; units the next block refuses wait at the unbatch, in order. A sink that receives a batch counts it once in `count` and `throughput`, with one cycle time from the batch's creation time; items passed on by an unbatch keep their own creation times. Work in progress counts items: a batch reaching a sink, or discarded by a `queue`, removes every item it holds. Proposed default (AKS-105), owner to confirm.
- **Store.** The stock on hand is a whole number, `initial` at time 0. An item arriving while stock is on hand takes one unit (a batch takes one unit, as one item) and is passed on at that instant; one arriving at zero stock is a stock-out, counted when it arrives, and waits, first in first out; a delivery adds `order_quantity` and the waiting items take its units in order at that instant, each still a stock-out. The store reviews its stock once at time 0 and after every withdrawal, and nowhere else (an item finding no stock withdraws nothing): "falls to `reorder_point`" means that the stock on hand plus on order is then at or below `reorder_point`, and each review that finds it so places one order of `order_quantity`, so several orders can be outstanding, and a position far below the reorder point orders once per withdrawal rather than enough at once to rise above it. Waiting items are not subtracted from the position, as the block reference writes it ("stock on hand plus on order"). Each order's `lead_time` is drawn from the store's own stream when the order is placed, and the delivery arrives that long after; an order whose delivery would be due at or after the end of the run never arrives. Proposed default (AKS-106), owner to confirm. With items of one unit each and at most one order outstanding at a time, this is the textbook (R, Q) policy with backorders, R the `reorder_point` and Q the `order_quantity`: an item that finds no stock withdraws only at the next delivery, but the next order still follows the Q-th withdrawal after the last one, and that withdrawal finds stock, so the orders fall where the textbook's do. The (R, Q) formulas then give the store's statistics; `templates/inventory_reorder_point` checks them (AKS-139, owner to confirm).
- **Pool.** A server with `pool` holds two things for each item it serves: one of its own units and one unit of the pool. An item arriving while one of the server's units is available takes it (otherwise it waits in the server's queue, as "Server queue" says) and then asks the pool for a unit; pool units go to the items asking, across all servers, in the order they asked. The item's wait, and its service, begin when it holds both; while it holds a server unit and waits for the pool unit it is waiting, not in service: it counts in the server's `queue_length` and in its waiting items for `shortest_queue`, and its unit is not busy in the server's `utilization`, though no other item can take that unit. `queue_capacity` limits only the items waiting for a server unit. A finished item refused by the next block keeps both its server unit and its pool unit until it moves ("Blocking"), and both are released together when it moves; the pool unit then goes to the item that asked first. A pool has no ports, so it is never a branch's route. A `schedule` may target a pool, and then changes the pool's capacity as it would a server's. A server's own statistics (`utilization`, `scheduled_fraction`, `availability`) are over its own units, whatever its pool does. Proposed default (AKS-107), owner to confirm.
- **Schedule.** The scheduled capacity of the target at time t is the sum of the `capacity` of every shift with `start` ≤ t mod `period` < `end`, and 0 where no shift is listed; overlapping shifts add up. It never exceeds the target's own `capacity` (its nominal capacity): a larger value is taken as the nominal capacity, since the target has no more units. The capacity at time 0 applies before any other event, and each later change is an event at its instant, run in scheduling order with the others due then ("Simultaneous events"). When the scheduled capacity rises, waiting items start at that instant, in the order the discipline gives. When it falls, no unit stops an item: a unit holding an item finishes it (and, if refused, holds it until it moves), and an item starts only while fewer units hold items than are available. Built in the adapter, since SimPy's resource capacity cannot change (DECISIONS, "Engine gap: SimPy lacks resource capacity that changes over time"). Proposed default (AKS-107), owner to confirm.
- **Failure.** One `failure` block is one alternating process on its target: it draws a `time_to_failure` from its own stream at time 0, and when that has passed one unit of the target fails and it draws a `time_to_repair`; when that has passed the unit is repaired and it draws the next `time_to_failure`. So at most one unit of the target is failed at a time, and the time to failure runs on calendar time from each repair, whether the units are busy, idle or off shift. The available capacity is the scheduled capacity minus the failed units, at least 0, so the failed unit counts against the units on shift. The unit that fails is an available unit holding no item if there is one; otherwise the unit of the item in service that started service last, and that item is suspended: it keeps its remaining service time, is not busy and not waiting while suspended, and resumes on the repaired unit with that remaining time, at the repair, even if its shift has ended; otherwise a unit holding a finished item that the next block refused, which still moves when space frees there; otherwise a unit whose item waits for a pool unit, and that item's service then begins only after the repair (it may hold the pool unit meanwhile). A unit freed while failed stays out of service until the repair. Proposed default (AKS-107), owner to confirm.
- **Ranges.** A server's, queue's or pool's `capacity`, a batch's `size`, a store's `order_quantity` and a source's `max_items` are at least 1, since a smaller value never passes an item; a `queue_capacity`, a store's `initial` and `reorder_point`, and a shift's `capacity` are at least 0; each weight is at least 0 and at least one is above 0; `first_arrival` and a shift's `start` are at least 0 s; `timeout` and `period` are above 0 s; a branch has at least one route; a shift's `end` is after its `start` and no later than `period`. A value outside these is E123 (spec 1). Proposed defaults (AKS-90), owner to confirm.

Proposed defaults chosen by the review council, owner to confirm; M4 may correct them with a DECISIONS entry:

- **Source when blocked.** A source whose next block cannot accept the item discards it and counts it in `<source>.discarded`; arrivals are never delayed. Built at M2 and checked by the queue, loss benchmark at M4 (AKS-105); still owner to confirm.
- **Failure.** `time_to_failure` is sampled from the failure block's stream and runs on calendar time while the unit is not failed, busy and idle alike. A failure takes one unit; an item in service on it is suspended and resumes with its remaining service time after repair (preempt-resume). `time_to_repair` runs from the moment of failure. Built at M4 as "Failure" above says, and checked by the failure benchmark (AKS-107); still owner to confirm.
- **Schedule.** `shifts` is a list of `{start, end, capacity}` with `start` and `end` time quantities within `period` and `capacity` an integer; the list repeats every `period`, and outside every listed shift the capacity is 0. A unit busy when scheduled capacity falls finishes its current item, then stops. Built at M4 as "Schedule" above says, and checked by the deterministic schedule benchmark (AKS-107); still owner to confirm.
- **Batch timeout.** When `timeout` elapses after a batch's first item arrived, the partial batch is released; an `unbatch` splits whatever it receives. A batch's cycle time is its first item's. Built at M4 as "Batch and unbatch" above says (AKS-105); the batch and unbatch benchmark has no timeout, so the timeout is checked by unit tests only; still owner to confirm.
- **Pool.** A server with `pool` seizes its own capacity first, then one pool unit; service, and therefore the end of the item's wait, begins only when both are held, and both are released after service; pool units are granted first come, first served across servers. Built at M4 as "Pool" above says, and checked by the resource pool benchmark (AKS-107); still owner to confirm.
- **Targets.** A server may be the target of at most one `schedule` and one `failure` (E125). Built at M1 (AKS-89) and checked against running models at M4 (AKS-107); still owner to confirm.

M2 built these five, with `shortest_queue` and `queue_capacity` (AKS-98, AKS-99), and runs them in the M2 benchmarks. M4 built `queue`, `batch` and `unbatch` (AKS-105), which run in the queue, loss and batch and unbatch benchmarks, `store` (AKS-106), which runs in the store, deterministic benchmark, and `resource_pool`, `schedule`, `failure` and a server's `pool` (AKS-107), which run in the resource pool, schedule, deterministic and failure benchmarks. Every block type now runs. The council's proposed defaults above are built as written and none was contradicted by a benchmark; all remain owner to confirm (AKS-76). ### Statistic definitions

| Statistic | Definition |
| --- | --- |
| `<server>.wait.mean` | Mean time from arrival at the server to start of service, over items whose service starts after warm-up |
| `<server>.utilization` | Busy time in the observed period divided by the integral over the period of available capacity (scheduled capacity minus failed units); without schedule or failure this equals busy time over capacity times the period. Busy time counts at each instant at most the available capacity: a unit finishing its item after scheduled capacity falls (see "Schedule") adds nothing, so utilization never exceeds 1. A unit holding an item its next block refused is busy (see "Blocking"; AKS-99, owner to confirm). A unit whose item waits for a pool unit, and the unit of an item suspended by a failure, are not busy; a server whose available capacity is 0 over the whole observed period has no utilization (NaN, like a mean over no items). Confirmed at M4 with a schedule and a failure (AKS-107; owner to confirm) |
| `<sink>.throughput` | Items reaching the sink after warm-up, divided by the observed period |
| `<sink>.cycle_time.mean` | Mean time from creation to sink, over items reaching the sink after warm-up |
| `<server>.availability` | Time at least one unit is not failed, over the period; 1 without a failure. Time-weighted over the observed period like the other time-weighted statistics. One `failure` fails one unit at a time ("Failure"), so a server of capacity 2 or more always has availability 1 (confirmed at M4, AKS-107; owner to confirm) |
| `<server>.scheduled_fraction` | Integral of scheduled capacity over nominal capacity times the period; 1 without a schedule. The integral is over the observed period, of the scheduled capacity capped at the nominal capacity ("Schedule"); the nominal capacity is the server's own `capacity`, and a schedule on its pool does not change it (confirmed at M4, AKS-107; owner to confirm) |
| `<server\|queue>.queue_length.mean` | Time-weighted average number waiting, not in service; for a queue, the items it holds, an item passing straight through not counted (see "Queue"; AKS-105, owner to confirm) |
| `<server\|queue>.queue_length.max` | Largest number waiting at any instant in the observed period |
| `<queue>.wait.mean` | Mean time an item spends in the queue, from its arrival to the moment it moves to the next block, over items moving on after warm-up; an item passing straight through counts 0 s, and a discarded item is not counted (confirmed at M4, AKS-105; owner to confirm) |
| `<batch>.wait.mean` | Mean time from an item's arrival at the batch to its release, the moment its batch moves on to the next block (later than forming when that block refuses it), over the items of batches moving on after warm-up, whenever each item arrived; a unit counts once, a batch of batches as its batches (confirmed at M4, AKS-105; owner to confirm) |
| `<pool>.utilization` | As a server, over the pool's units: the granted pool units, counted at each instant at most up to the pool's available (scheduled) capacity, integrated over the observed period and divided by the integral of that capacity; a pool unit held by a finished item refused downstream is busy; NaN when the pool has no capacity over the whole period (confirmed at M4, AKS-107; owner to confirm) |
| `<store>.stock.mean` | Time-weighted stock on hand over the observed period; units taken by items refused downstream are no longer on hand (confirmed at M4, AKS-106; owner to confirm) |
| `<store>.stockouts` | Items that found stock at zero, counted when they arrive, at or after warm-up: a count of items, like `<sink>.count`, not a rate; an item that arrives before warm-up and gets its unit after it is not counted (confirmed at M4, AKS-106; owner to confirm) |
| `<store>.orders` | Orders placed at or after warm-up, counted when placed, divided by the period: a rate, like throughput (confirmed at M4, AKS-106; owner to confirm) |
| `<source>.created` | Items created after warm-up |
| `<sink>.count` | Items reaching the sink after warm-up |
| `<source>.discarded`, `<queue>.discarded` | Items discarded after warm-up, divided by the period: a rate, like throughput. A source discards an item its next block refuses; a `queue` with `on_full` `discard` an item arriving when it is full; a batch discarded counts once (confirmed at M4, AKS-105; owner to confirm) |
| `model.wip.mean` | Time-weighted number of items in the system: created and not yet at a sink or discarded |

- The observed period runs from the end of warm-up to the end of the run.
- An event at exactly the end of warm-up belongs to the observed period: counts and observations take events at or after warm-up (an item reaching a sink at that instant counts, and so does a wait whose service starts then). Time-weighted statistics integrate only over the period, so an item in service across the end of warm-up adds only the part of its service after it. `queue_length.max` is the largest of the value held at the end of warm-up and every value taken during the period, including one held for no time. Proposed default (AKS-98), owner to confirm.
- A mean over no items (`wait.mean` or `cycle_time.mean` in a replication where no item qualifies) is undefined, and the replication's value is NaN (spec 1 "Tables for the `process` domain"). Proposed default (AKS-98), owner to confirm.
- Items still in the system at the end are not counted in waits or cycle times.
- Across replications: the reported mean is the mean of replication means. The half-width is t(1 − (1 − confidence)/2, n − 1) times the sample standard deviation of the replication means (n − 1 denominator), divided by √n. The t quantile comes from `scipy.stats.t.ppf`; no table is hard-coded. Per-replication statistics are the adapter's; this across-replication line is computed by the experiment manager for every adapter.
- A replication value that is NaN (a mean over no items, above) is left out: the mean and half-width are over the n values that remain, with t at n − 1 degrees of freedom, and `summary.json` reports n with each metric (spec 1 "Run folder and results"). With n = 1 the half-width is undefined, and with n = 0 the mean too; an undefined value is written `null`. Proposed default (AKS-102), owner to confirm.
- Between scenarios: for each metric and each pair of scenarios the difference is computed per replication (same replication number, same streams) and reported as a mean with a half-width from the paired differences; an interval excluding zero is reported as separated. Precisely (AKS-102, proposed default, owner to confirm): each pair is taken in the experiment's scenario order and the difference is the later scenario's value minus the earlier's; a replication is paired only when both values are not NaN, and n is the number of pairs; the mean and half-width follow the across-replication rule at the experiment's `confidence`; separated means n ≥ 2 and |mean| > half-width (strict, so a difference of exactly 0 with no spread is not separated).
- Time series are recorded every `record_interval` for every time-persistent statistic, in the `timeseries` table of spec 1. In M2 these are, per server, `<server>.queue_length` (items waiting) and `<server>.utilization` (busy units, blocked ones included, over `capacity`), and `model.wip` (items in the system); each is its summary metric without `.mean`, so its time average is that metric. From M4 each `queue` adds `<queue>.queue_length`, for its `queue_length.mean`; a `batch` and an `unbatch` add none, since `<batch>.wait.mean` is not time-persistent (AKS-105, owner to confirm). Each `resource_pool` adds `<pool>.utilization` (AKS-107, owner to confirm). For a server or pool with a schedule or a failure, a `utilization` sample is the busy units, at most the available capacity, over the available capacity, and 0 while no capacity is available; its time average is then not the summary metric, which is a ratio of two integrals. Without a schedule or failure it is busy units over `capacity`, as before. Each `store` adds `<store>.stock`, the stock on hand, for its `stock.mean`; `<store>.stockouts` and `<store>.orders` are counts, not time-persistent, so they have none, whatever the summary's "each comes as … a time series" says (AKS-106, owner to confirm). Samples are taken at k × `record_interval` for k = 0, 1, 2, … while the time is before the end of the run, from the run start and through warm-up, so there is a sample at 0 s and none at the end. A time short of the end by less than a billionth of `record_interval` counts as the end, so the rounding of `length` / 200 (for example 200 × (29 s / 200) is just below 29 s) never adds a 201st sample. A sample is the value after every event due at that instant. Sampling adds no event and draws no random number, so it changes no other result. Proposed default (AKS-99), owner to confirm.
- Warm-up check (kept over MSER-5 and Welch's method by the M3 research note `docs/research/spec-2-output-analysis.md`; the 99% level and the 5% threshold are proposed defaults, owner to confirm): for each time-persistent statistic the means over the first and second halves of the observed period are compared across replications as a paired difference; if the 99% interval excludes zero and the difference exceeds 5% of the mean, `summary.json` carries W210. The 99% level is chosen because a 95% interval would flag about one correct steady-state run in twenty per statistic. Precisely (AKS-129):
  - **Input.** Every metric of the run's `timeseries` table (in M2 `<server>.queue_length`, `<server>.utilization` and `model.wip`), for each scenario of the experiment. A replication's observed samples are its samples with `time_s` at or after `warmup` (the same boundary as every other statistic), in time order; J is their number, the same in every replication. The check uses the samples as they are, not a time-weighted integral.
  - **Halves.** With h = ⌊J/2⌋, the first half is the first h observed samples and the second half the last h; when J is odd the middle sample is in neither. A metric with J < 2 is not checked.
  - **Statistic.** For replication r of n: d_r = (mean of the second half) − (mean of the first half), and m_r = the mean of all J observed samples. d̄ and m̄ are the means of the d_r and the m_r over the n replications; s is the sample standard deviation of the d_r (n − 1 denominator), and the half-width is t(0.995, n − 1) × s / √n, with t from `scipy.stats.t.ppf`. The level is 99% whatever the experiment's `confidence`. n is at least 2 (E170), so the quantile is always defined; when s is 0 the half-width is 0.
  - **Changed.** A metric has changed in a scenario when |d̄| > half-width and |d̄| > 0.05 × |m̄| (both strict). A constant series has d̄ = 0 and never changes. A metric with m̄ = 0 is not reported as changed, since a change as a percentage of its mean is undefined; every Phase 1 series is at least 0, so its m̄ is 0 only when every sample is (AKS-102, owner to confirm).
  - **Warning.** When at least one metric has changed in at least one scenario, `summary.json` `warnings` carries exactly one W210 issue for the run, not one per metric: `component` null; `path` `/experiments/<index>/warmup`, the experiment's position in the model file's `experiments` array (where the key belongs when `warmup` is absent); `message` "Results were still changing after warm-up: " followed by, for each changed metric in scenario order and then `timeseries` row order, "<metric> in scenario <scenario> changed by <p>% of its mean between the first and second halves of the observed period", joined by "; " and ending with a full stop, where p is 100 × |d̄| / |m̄| rounded to the nearest whole number (a half rounds up; AKS-102); `hint` "Lengthen 'warmup' and run again.". The W210 issue follows the adapter's warnings in `warnings` (spec 1 "Run folder and results"). The check computes nothing else and changes no other result.
  - **Scope.** A plain experiment, and of a search only the best candidate's confirmation, whose results the summary reports, its scenario named `default` (decided at M5, AKS-109, owner to confirm; see "Simulation-based optimization").
  - Simplest readings of the proposal (AKS-129), owner to confirm: the samples rather than a time-weighted integral, the halves by sample count, one warning per run, its path, message and hint, and the scope.

How the M2 benchmark files read the table above (AKS-100, proposed default, owner to confirm):

- **Distributions.** Every arrival and service time in the M2 cases is exponential, and so is the delay's time; "Arrivals 30/h" is an exponential interarrival time of mean 2 min. Burke's theorem needs Poisson arrivals and exponential service at A for the tandem answers; the delay (Little) and branch (split) answers hold for any distribution but use the same arrivals.
- **Branch case.** One source feeds a branch with `rule` `probability`, routes `a` and `b` and weights 0.3 and 0.7; route `a` goes to sink `sink_a` and `b` to `sink_b`.
- **Metric names.** Each known answer is one metric the process adapter reports for one replication (spec 1 "Metric names"): a server's `wait.mean`, `queue_length.mean` and `utilization`, a sink's `cycle_time.mean` and `throughput`, and `model.wip.mean`. "Throughput" is the sink's; "cycle time" is the sink's, from creation, so the tandem's 8.000 min covers both stations.
- **Values.** `value` in `expected.json` is in the units the adapter reports: seconds for times, items per second for rates, and plain numbers otherwise (4.500 min is 270 s; 30.0/h is 1/120 per second). It is the exact closed-form value, not the rounding shown above (1.929 min is 810/7 s).
- **Estimate and standard error.** The estimate is the mean of the 100 replication values of the metric; the standard error is their sample standard deviation (n − 1 denominator) divided by √n. A missing metric or a NaN replication value fails the check.
- **Exact.** An `exact` check passes when the estimate and the known answer, each rounded to four significant figures, are equal.
- **Coverage run.** For each case, `pytest -m benchmark_coverage` runs the model with 20 consecutive seeds, starting at the seed in `model.json`; a seed passes when every check of the case passes, and the case passes the coverage run at 19 of 20 or better.

### Mathematical optimization in the model file

A model with `"domain": "optimization"` uses `variables`, `objective` and `constraints` in place of components. This layout runs from M5 in the HiGHS adapter `highs` (AKS-108), as below.

```json
{
  "format_version": "0.1",
  "meta": {"name": "Product mix"},
  "domain": "optimization",
  "variables": [
    {"id": "chairs", "type": "continuous", "lower": 0},
    {"id": "tables", "type": "continuous", "lower": 0}
  ],
  "objective": {"sense": "maximize", "linear": {"chairs": 45, "tables": 80}},
  "constraints": [
    {"id": "wood",   "linear": {"chairs": 5,  "tables": 20}, "op": "<=", "rhs": 400},
    {"id": "labour", "linear": {"chairs": 10, "tables": 15}, "op": "<=", "rhs": 450}
  ]
}
```

- Variable types: `continuous`, `integer`, `binary`. `lower` and `upper` are plain numbers; a bound left out means no bound on that side (write `"lower": 0` for a non-negative variable).
- `objective.sense` is `minimize` or `maximize`; a constraint's `op` is `<=`, `>=` or `==`; coefficients and `rhs` are plain numbers.
- Phase 1 supports linear objectives and constraints only.
- Results report each variable's value, the objective value, and for each constraint whether it is tight.
- Indexed problems, such as a transport plan over many routes, use sets and tables (format 0.2, below).

**Indexed problems** (AKS-123, built for the transport plan template; owner to confirm). Spec 1 "Top-level keys" gives the keys and their issue codes. A set names the members a decision or limit repeats over; a table gives a number per member, or per combination of members; a variable with `over` stands for one variable per combination of members of its sets, a constraint with `for` for one constraint per combination of members of its sets, and a term adds a variable times a coefficient, summed over the variable's sets that the constraint's `for` does not name. The transport plan, three depots supplying four customers at a cost per crate on each route:

```json
{
  "format_version": "0.2",
  "meta": {"name": "Transport plan"},
  "domain": "optimization",
  "sets": {"depots": ["north", "centre", "south"],
           "customers": ["city", "harbour", "park", "market"]},
  "tables": {
    "supply": {"over": ["depots"], "values": {"north": 300, "centre": 200, "south": 250}},
    "demand": {"over": ["customers"],
               "values": {"city": 180, "harbour": 220, "park": 150, "market": 170}},
    "cost": {"over": ["depots", "customers"], "values": {
      "north":  {"city": 4, "harbour": 6, "park": 9, "market": 5},
      "centre": {"city": 7, "harbour": 3, "park": 5, "market": 8},
      "south":  {"city": 6, "harbour": 8, "park": 4, "market": 3}}}
  },
  "variables": [{"id": "ship", "type": "continuous", "lower": 0, "over": ["depots", "customers"]}],
  "objective": {"sense": "minimize",
                "terms": [{"variable": "ship", "coefficient": {"$table": "cost"}}]},
  "constraints": [
    {"id": "supply", "for": ["depots"], "terms": [{"variable": "ship"}],
     "op": "<=", "rhs": {"$table": "supply"}},
    {"id": "demand", "for": ["customers"], "terms": [{"variable": "ship"}],
     "op": ">=", "rhs": {"$table": "demand"}}
  ]
}
```

- **Expansion.** Before the adapter sees it, an indexed model is written out as the flat layout above, so the adapter, `summary.json`, the findings and the results views work on it unchanged. A variable `ship` over `depots` and `customers` becomes one variable per combination, named `ship[north,city]`: the id, then the members in the order of `over`, comma-separated without spaces, in square brackets; it keeps the declared `type`, `lower` and `upper`. A constraint `supply` for `depots` becomes `supply[north]`, `supply[centre]` and `supply[south]`. A variable or constraint with no sets keeps its id. Combinations follow the order of the members, the first set outermost; the expanded variables follow the declared variables' order, and the expanded constraints the declared constraints'. A name with brackets is not an identifier, so it never clashes with a declared id.
- **Coefficients.** In each expanded constraint (or the objective, which has no `for`), a term adds, for each combination of the term variable's sets not in `for`, the variable named by the constraint's members and that combination, with the coefficient: the plain number, or the table's value at the members of the table's own sets. Coefficients of one variable from several terms or from `linear` add up; a coefficient of 0 is kept; a sum too large for a float is E123 at the term's `coefficient` (review of PR #53). `rhs` is the plain number or the table's value at the constraint's members.
- **Results.** `summary.json` reports the expanded names (`"variables": {"ship[north,city]": 180, ...}`, `"constraints": {"supply[north]": {...}, ...}`); an expected value names one as `variables.ship[north,city]`.
- **Limits of this layout.** A variable is indexed over distinct sets (a set twice in one `over` is E178), so a flow between members of one set, such as a network over its own nodes, waits for aliases (Phase 2). Bounds are plain numbers, the same for every member; a per-member bound is a constraint with `for`. Tables hold plain numbers only.

`summary.json` for `optimization` is:

```json
{"model": "Product mix", "status": "optimal", "objective": 2200,
 "variables": {"chairs": 24, "tables": 14},
 "constraints": {"wood": {"tight": true, "slack": 0},
                 "labour": {"tight": true, "slack": 0}}}
```

`status` is `optimal`, `infeasible` or `unbounded`; `experiments` is absent and `run` still applies.

How the HiGHS adapter fills it (AKS-108, from `docs/research/spec-2-solver-layer.md`; proposed default, owner to confirm):

- **Solve.** HiGHS through Pyomo's `pyomo.contrib.solver` interface (`SolverFactory("highs")`), in-process through `highspy`, with HiGHS's default options and no time limit of its own: the run target's limits (spec 1, E192) apply.
- **Status.** Pyomo's termination condition `convergenceCriteriaSatisfied` is `optimal`; `provenInfeasible` and `locallyInfeasible` are `infeasible`; `unbounded` is `unbounded`. `infeasibleOrUnbounded`, which HiGHS can leave for an integer program after presolve, is settled by one more solve with HiGHS's `presolve` `off`, mapped the same way. Any other ending, or `infeasibleOrUnbounded` again, has no `status` of the three, so the run fails with E190 and `log.txt` names the condition.
- **Values.** `objective` and each variable's value are HiGHS's, not rounded (the product mix gives 24.000000000000004 chairs; the interface chooses the display). For `infeasible` and `unbounded`, `objective` is `null` and `variables` and `constraints` are empty objects: an unbounded program has no optimum to report.
- **Slack and tight.** A constraint's `slack` is `rhs` minus its left-hand side for `<=`, the left-hand side minus `rhs` for `>=`, and minus the distance between them for `==`; it is not rounded (the product mix's binding `wood` constraint has slack 5.7e-14, not the 0 of the example above). A constraint is `tight` when |`slack`| ≤ 10⁻⁶, at least as loose as HiGHS's default feasibility tolerances (10⁻⁷ for a linear program, 10⁻⁶ for an integer one).
- **Edge cases.** A constraint whose `linear` is empty has the left-hand side 0 and is judged without the solver, exactly: one that does not hold makes the model `infeasible`. A model with no variables is `optimal` with `objective` 0 when every constraint holds. A variable that neither the objective nor any constraint names still gets a value within its bounds.
- **Duals.** `summary.json` holds no duals. For a model whose variables are all `continuous`, the adapter's own output (`engine/output/solution.json`, spec 1 "Division of labour") records each constraint's dual, the change in the objective per unit increase of its `rhs`; an integer program has none.

### Simulation-based optimization

- **Where.** An experiment with a `search` object (spec 1).
- **Variables** are the parameters it names.
- **Baseline.** The model's current values are always the first candidate.
- **Search.** If the number of distinct integer combinations is at most the budget, every combination is run; otherwise Optuna's TPE sampler proposes candidates, seeded from the spec 1 stream key `<seed>:0:optimizer` (`optimizer` is a reserved identifier), so a search repeats exactly.
- **Budget** is a number of candidates, default 50; each runs `search.replications` with the experiment seed (common random numbers).
- **Confirmation.** The baseline and the best three candidates by search-stage mean objective among those whose search-stage means satisfy the constraints are re-run with the experiment's full `replications`; constraints are re-judged on the confirmed means, and the reported best is the best confirmed feasible candidate, the baseline included (it is always confirmed, whatever its search-stage result). If none of the three is feasible on confirmation, the next three feasible-at-search candidates are confirmed, until one is feasible or none remain. If no other candidate is confirmed feasible and the baseline is, the baseline is the best and `after` equals `before`. Only when no confirmed candidate, baseline included, is feasible is `status` `infeasible`, with the baseline's confirmed metrics reported. The result states whether the best is separated from the confirmed runner-up (paired difference interval excluding zero).
- **Constraints** on simulated metrics are judged on the confirmed mean.
- **Result.** `summary.json` gains `search: {best: {set}, objective: {metric, before, after}, separated: bool, candidates: [{set, metrics, feasible, confirmed}]}`, where `before` is the baseline's confirmed objective.

Built at M5 (AKS-109) in `src/ithax/runs/search.py`, inside the experiment manager, and verified by `tests/runs/test_search.py` (the machine-count test on both paths and the baseline-only-feasible case), `tests/runs/test_local_search.py` and `benchmarks/machine_count`. The M5 research note (`docs/research/spec-2-simulation-based-optimization.md`) keeps the fixed top-three confirmation: no ranking-and-selection procedure replaces it in Phase 1 (KN with common random numbers and Batur and Kim's feasibility check are the Phase 2 candidate, owner to confirm). The readings it was built to (AKS-109, from the research note's recipe where it gives one; owner to confirm):

- **Candidates.** A candidate is one value per variable, in `search.variables` order. It is run as the experiment with one scenario, `default`, whose `set` holds those values, and nothing else changed: the same seed, `length`, `warmup` and `record_interval`, with `search.replications` replications at the search stage and the experiment's `replications` at confirmation. Each run is one `translate`, `run` and `collect` in its own subfolder of `engine/` (spec 1 "Division of labour"): `search-<n>` for candidate n's search stage and `confirm-<n>` for its confirmation, n counted from `000`, the baseline.
- **Which path.** The exhaustive path is taken when every variable is an `integer` parameter and the product of their ranges (`max` − `min` + 1 each) is at most `budget`; it runs the baseline, then every other combination in order, the first variable changing slowest. A `number` or `quantity` variable has no finite set of values, so a search with one always uses Optuna, which suggests it as a float between `min` and `max` (a `quantity` in seconds).
- **Optuna.** Logging at `WARNING`; the sampler seed is the first draw `integers(0, 2**32)` of the generator of `<seed>:0:optimizer`, since the sampler seeds a `numpy.random.RandomState`, which accepts no larger seed, and nothing else draws from that stream; `TPESampler(seed=...)` with every other argument at its default; an in-memory study in the objective's direction; the baseline enqueued as trial 0; ask and tell one trial at a time, never in parallel (parallel trials reseed the sampler from the operating system); `suggest_int` for an `integer` variable and `suggest_float` otherwise, in `search.variables` order; one `Trial.set_constraint` per constraint, `value` − mean for `>=` and mean − `value` for `<=` (feasible at 0 or less), infinity when the mean is undefined; the search-stage mean objective told, or a failed trial when it is undefined.
- **Repeated suggestions.** The sampler can suggest a candidate already evaluated. It is not run again: the trial is told the stored search-stage results, and it does not count against `budget`. Asking stops when `budget` distinct candidates, the baseline included, have been evaluated, or after 10 × `budget` asks; a search stopped by that cap reports the candidates it has.
- **Repeats.** A seeded search repeats exactly on the same Optuna and numpy versions (spec 1 "Identical runs"); Optuna 4.x, 4.9.0 and 5.0.0 give different sequences from the same seed (research note), so the manifest's `optimizer` records the method and the Optuna version (spec 1 "Run folder and results").
- **Feasible** means the objective's mean is defined and every constraint in the model's `constraints` holds on the means; a constraint on an undefined mean does not hold. A candidate whose objective mean is undefined is never feasible.
- **Ranking.** Candidates are ranked by mean objective in the objective's sense; equal means are ranked by candidate order, the earlier first. The confirmation groups exclude the baseline, which is confirmed first in any case.
- **Overlap of the two stages.** The confirmation replications are numbered from 0, like the search stage's, with the experiment seed, so a candidate's first `search.replications` confirmed values are its search-stage values and only the rest are new. The confirmed means dilute the search stage's selection bias but do not remove it. This is spec 2 as written; numbering the confirmation replications from `search.replications` instead would make them disjoint and keep common random numbers across confirmed candidates. Owner to decide (research note, "Overlap of the two stages").
- **Separated.** The paired difference of the objective metric, best minus runner-up, over the replications both confirmations report (same replication number, NaN pairs left out), at the experiment's `confidence`, with the rule of "Between scenarios" above. The runner-up is the next confirmed feasible candidate by the ranking; with none, `separated` is `false`. With `status` `infeasible`, `separated` is `false`.
- **Result layout.** `search` holds `status` (`feasible`, or `infeasible` when no confirmed candidate is), then `best`, `objective`, `separated` and `candidates`, as above. `best.set` and each candidate's `set` give the variables' values in SI units, like a scenario's `set`. `candidates` lists every candidate in the order it was evaluated, the baseline first; a candidate's `metrics` (every metric of its `replications` table as `{mean, half_width, unit, n}`) and `feasible` are its confirmation's when `confirmed` is `true`, and its search stage's otherwise, so `n` shows which. `before` and `after` are the baseline's and the best's confirmed mean objective (`null` when undefined).
- **The rest of `summary.json`.** A search run's `summary.json` is the process layout of spec 1 for the best candidate's confirmation, then `search`: `replications` is the experiment's, `scenarios` holds the one scenario `default` with the best candidate's `set` and confirmed metrics, `differences` is empty, and `tables/` holds that confirmation's tables. With `status` `infeasible` the best is the baseline.
- **Warm-up check.** W210 (see "Statistic definitions") is checked on the best candidate's confirmation, the results the summary reports, and names its scenario `default`. The search-stage runs and the other confirmations are not checked.
- **Scenarios.** A search runs its own candidates, so an experiment with a `search` lists no scenarios (E171, spec 1 "Experiments").
