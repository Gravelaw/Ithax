# Answering a review finding

The build guide's "Review findings" procedure (owner decision F2; retrospective P7).

1. Verify the finding against the code at the PR's head. Write the failing case first: a test, fixture or probe that shows the defect, or the spec section or invariant that makes it unreachable.
2. Classify the finding against the classes in `AGENTS.md` "Code Review Rules".
   - If it is the second finding of one class in this PR, stop patching sites one at a time:
     - find every site of the class in the repository;
     - fix them all through one shared helper;
     - add a check that catches the next one (a lint rule, a conventions test or a property test);
     - add a bullet to `AGENTS.md`.
3. Fix it with its test, then follow the `pre-push` skill before pushing.
4. Reply on the thread in exactly one of these forms, with the GitHub footer:
   - *Fixed in `<sha>`*
   - *Fixed for the whole class in `<sha>`*: say what the new check is.
   - *Not a defect: `<the spec section or invariant that makes it unreachable>`*
   - The footer:

     ```
     ---
     _Generated by [Claude Code](https://claude.ai/code)_
     ```
5. Resolve the thread once the fix is pushed, or once the reply shows the finding is not a defect.
   - Leave a security finding open for the owner.
6. Before reporting the PR ready, check that Codex's last review refers to the current head SHA, and that no thread is unresolved (guide "Merge readiness").
